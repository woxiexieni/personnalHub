# 事件时间块、目标层与 OPDCA 闭环 v0.1（需求边界）

> 状态：**已确认（2026-10-18）**，待定项已拍定，可直接开工 R2
> 范围：**新增**「时间块」这条高频路径（低成本的记录方式）；新增长目标层；把 OPDCA 定为顶层迭代节奏。**不取代、不改动**已有的「事件反思」（§4.7）
> 上游依据：`产品需求总览-v1.0.md`（已冻结）、`分析功能需求-v0.1.md`（统计口径）
> 本版不涉及：资产（Asset）独立实体、自动识别手机 App 使用时长、通知栏常驻、待办清单

---

## 0. 一句话

**把「你在做什么」的采集成本压到一次点击；把「你想做成什么」变成一条能看出还在不在动的线。**

拆成两个可验收的条件：

1. **块**：录入一次 ≤ 1 次点击、0 打字，否则样本不够；
2. **线**：目标只回答"累计投入多少、几天没动、这几周有没有推进"，不回答"完成百分之几"。

---

## 1. 为什么推翻旧表单（留下裁判条款）

旧方案：10 个字段，9 个是必填文本框（标题 / 简述 / 想法 / 行动 / 结果 / 反思 / 计划 …）。

死亡原因不是"字段多"，而是**每条都要现场组织语言**。组织语言的成本远高于打字，人一天只够用一两次，而想记的行为一天有十几次。这个表单在设计上就只能当"出大事了写一篇"的工具。

**裁判条款（后续所有录入功能都适用）**

> 1. 任何录入字段，如果要求用户"现场组织语言"，必须满足：可选、默认收起、不填也能保存。
> 2. **打字预算与录入频次成反比。** 一季度写 3 次的表（目标）可以打字；一天点 10 次的层（时间块）一个字段都不许打字。
> 3. **需要用户维护的状态，一律改算。** 能不让他"标记完成/标记停滞"，就不让他标。

第 2 条是三层结构的由来，第 3 条决定了目标的"停滞"是算出来的而不是设出来的。

---

## 2. 三层结构

| 层 | 数量级 | 录入频次 | 允许打字 | 版本 |
|---|---|---|---|---|
| **目标 Goal** | 同时活跃 ≤ 3 | 一季度 3~5 次 | 是（名字 + 一条下一步） | R2（极简） |
| **计划 Plan** | 每天 3 条 | 每天 3 次点击 | 否 | R4 |
| **时间块 Block** | 一天 10+ 条 | 一天 10+ 次 | **一个字段都不许** | R2 |

只有块层是高频的，所以只有块层被严格约束。上层数量少，打字成本可摊销。

**目标与事情片是正交的两个维度**：目标"做 PersonalHub"会消耗多种片（写代码 / 写文档 / 学技术 / 开会），所以目标不是片下面的分类。

## 3. 数据模型

### 3.1 时间块（`blocks` 表）

> **这是一张新表，与「事件反思」的 `things` 表无关。** 两者的分工见 §4.7，不要合并。

**「记一笔」和（将来的）「计一次」是同一个实体**，不是两张表。

| 字段 | 类型 | 说明 | 可空 |
|---|---|---|---|
| `id` | string | 客户端生成 Guid，Upsert 幂等靠它 | 否 |
| `piece_code` | string | 事情片 code（见 §4.1），如 `code` / `video` | 否 |
| `goal_id` | string | 归属目标。空 = 不归任何目标（吃饭、通勤） | 是 |
| `note` | string | 一句话备注 | 是 |
| `duration_min` | int | 时长（分钟）。0 = 未定（R2 无计时，此项恒有值） | 是 |
| `started_at` | int64 | 开始时间（Unix 毫秒）。0 = 手动补录 | 是 |
| `ended_at` | int64 | 结束时间（Unix 毫秒）。R2.5 起启用 | 是 |
| `worth` | int | 0 未评 / 1 值得再来 / 2 一般 / 3 别做了 | 是 |
| `lesson` | string | 一句话经验（仅 `worth=1` 时可填） | 是 |
| `plan_id` | string | 关联的当日计划项（§6.3），空 = 计划外 | 是 |
| `anomaly` | int | 0 正常 / 1 跨天未停 / 2 超长未停（R2.5 起启用） | 是 |
| `mood` | int | 状态 1~5。**本版不采集**，字段保留 | 是 |
| `occurred_at` | int64 | 归属时间（Unix 毫秒），见 §3.3 | 否 |
| `created_at` / `updated_at` | int64 | 创建 / 最后修改（Unix 毫秒） | 否 |
| `deleted` | bool | 软删，与 `records` 一致 | 否 |
| `synced` / `synced_at` | bool / int64 | 仅本地，不入 proto | — |

「完成几个番茄」不设字段，由 `floor(duration_min / 25)` 派生（不做暂停，所以准）。派生指标一律不入表，与 §7.6 的 Asset 原则一致。

### 3.2 目标（`goals` 表）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | Guid |
| `title` | string | 目标名，唯一必填项（一季度写几次，可承受） |
| `status` | int | 0 进行中 / 1 暂停 / 2 已完成 / 3 已放弃 |
| `next_step` | string | **一条**下一步，可空。不是列表 |
| `is_current` | int | 0/1。全局唯一，被"钉住"的那个 |
| `started_at` | int64 | 开始时间 |
| `created_at` / `updated_at` | int64 | — |
| `deleted` | bool | 软删 |

**以下三个指标全部是查询结果，不存字段**

| 指标 | 算法 |
|---|---|
| 累计投入 | `SUM(duration_min)` where `goal_id = g.id` |
| 最后活动 | `MAX(occurred_at)` where `goal_id = g.id` |
| 最近四周趋势 | 按周分组 `SUM(duration_min)`，缺失周补 0 |

**不存 `last_active_at`**：块被删或改归属时，存的值就错了。派生永远一致。

**目标不设截止日期**（已定）。没有超期失败，只有"还在不在动"。

### 3.3 归属规则

- **块的归属日期 = `started_at` 所在的自然日**（手动补录时为 `occurred_at`）。固定 UTC+8，与 `Period.StartOfDay` 一致。
- 跨 0 点的块整体归开始那天，**不劈开**（事项被劈开会让复盘列表断裂）。记账不受影响——记账是时点，无区间。
- **块的目标归属 = `is_current=1` 的那个目标**，录入时自动带，事后可改（见 §4.4）。
- `goal_id` 允许为空。吃饭、通勤、刷手机不归任何目标，这是正常数据，不是缺陷。

### 3.4 时长计算（R2.5 起）

```
duration_min = max(1, floor((ended_at - started_at) / 60000))
```

下限 1 分钟：点了开始就说明在做了。上限不设，> 4 小时交异常确认。

## 4. 录入：一次点击，零打字

### 4.1 事情片（一级，23 个）

| 组 | 片（`piece_code`） |
|---|---|
| 产出 | 写代码 `code` · 写文档 `doc` · 开会 `meeting` |
| 学习 | 学技术 `learn` · 刷题 `leetcode` · 读专业书 `book` · 学英语 `english` |
| 身体 | 运动 `sport` · 午睡 `nap` · 吃饭 `meal` |
| 生活 | 通勤 `commute` · 家务 `chore` · 收拾 `tidy` · 杂事 `errand` |
| 人际 | 聊天 `chat` · 陪家人 `family` · 聚餐 `dinner` |
| 消耗 | 短视频 `video` · 游戏 `game` · 看剧 `show` · 无目的刷手机 `scroll` |
| 零散 | 发呆 `idle` · 写复盘 `review` |

**排序规则（已定）**

1. **钉子优先**：长按可钉住，钉住的片固定在前排，顺序可拖。
2. 未钉住的按**最近 7 天点击频次**降序补满前排（默认前排 6 个）。
3. 其余按组折叠。

> 为什么不是纯频次：频次排序会让位置天天漂。你今天多点了几次短视频，明天"写代码"就从第一行挪走，肌肉记忆失效，每次都要找——省下的决策又还回去了。钉子把"你的常用"固化，"频次"只负责填空。

**其他规则**

- 只有一级，不做树。`piece_code` 生成后不改（统计要对得上历史），**显示名可随时改**。
- 可隐藏 / 新增片；新增时自动生成 `piece_code = p_<8位>`。

### 4.2 时长档

`5 / 15 / 30 / 60 / 120 / 180 分钟` + `自定义`。

默认值 = 上一次同片用的时长 → 多数时候**连这一下都不用点**。

`180` 是刻意加的：写代码 / 做项目经常一次超过 2 小时，只到 120 会逼人合并或拆错。

### 4.3 点击预算（验收用）

| 场景 | 点击数 |
|---|---|
| 只点片 + 用默认时长 | **1 次**（点完即存） |
| 片 + 换时长 | 2 次 |

**上限 2 次**。打开 App 到存下一条 ≤ 5 秒，不弹"保存成功"，存完即回列表。

### 4.4 目标归属：默认继承，事后可改

录入时**不选目标**。所有新块自动挂到 `is_current=1` 的目标（没有当前目标则 `goal_id` 为空）。

- 切目标只在目标页点一次「设为当前」，不是每次录入都点。
- 归错了就改：今日列表长按 → 换目标，或复盘时批量改。
- **不采用"自动继承最近活跃"**：你在两个项目间切换时会静默归错，而且错得不可预测。可预测比聪明重要。

### 4.5 状态：本版砍掉

录入时的 `mood`（1~5）不做，字段保留恒 0。

理由：复盘的 `worth`（值得 / 一般 / 别做）已经承载评价，录入再问一次是同一件事问两遍，纯多一次决策。

### 4.6 允许半条记录

只有 `piece_code` 也能存：时长空着、备注空着、`worth` 未评。**新建的 `BlockStore` 不得要求除 `piece_code` 外的任何字段**。这是硬约束——旧表单正是死在"全必填"上。

### 4.7 时间块 vs 事件反思：两张表，两个入口，不合并

**它们回答两个不同的问题，所以是两套东西。**

| | 时间块（`blocks`） | 事件反思（`things`，已存在） |
|---|---|---|
| 回答什么 | 时间去哪了 | 我对这类事的反应模式 |
| 频次 | 一天 6~10 条 | 一周 0~2 条 |
| 录入成本 | **1 次点击** | 9 段，愿意写才写 |
| 粒度 | 一段连续投入 | 一个瞬间 / 一件事 |
| 读法 | 按片聚合分钟数 | 按标签检索、看反复出现的模式 |
| 数据来源 | 新建 | R1 已上线，原样保留 |
| 版本 | R2 | 已完成，R2 不改动 |

**为什么不能合成一张表（我上一版写错了）**

1. **旧数据不合法。** R1 的 `things` 里有真实记录，它们没有 `piece_code`。合成一张表意味着要么给几十条旧记录编一个假片，要么让必填字段破例为可空——前者污染统计，后者等于没有约束。
2. **统计口径不同。** 时间块要 `SUM(duration_min) GROUP BY piece_code`；事件反思没有时长，按标签检索。合表后**每个查询都要多带一个 `kind` 条件**，忘一次就串数据。
3. **语义会互相挤压。** 一场 20 分钟的人际冲突，你会写一篇 9 段反思，但它不是一个"时间投入"。为了存进时间块，你得给它选一个片（比如"聊天"）——那一刻统计就被污染了，而且往后每次看"聊天 8 小时"都会怀疑。

**成本为什么很低**：同步链路已经是泛型的。现在 `MauiProgram` 里已经并存两套登记：

```
LocalRecordStore<LocalRecord> / IRecordUploader<LocalRecord> / RecordSyncService<LocalRecord>
LocalRecordStore<ThingRecord> / IRecordUploader<ThingRecord> / RecordSyncService<ThingRecord>
```

加时间块 = 照着再登记一套 `LocalBlock` / `BlockUploader` / `RecordSyncService<LocalBlock>`，**不改旧代码一行**。服务端同理：`BlockStore` + `BlockServiceImpl` + 一个 proto message，`ThingStore` 一行不动。

**入口怎么分**：录入目录三项。

| 目录项 | 小字 | 点击成本 |
|---|---|---|
| 账单 | 今日 X 笔 | 已有 |
| **时间块** | 今天已记 X 条 · 共 Y 小时 | 1 次 |
| 事件反思 | 想深挖一件事时用 | 9 段 |

用户不会困惑"该点哪个"，因为动机不重叠：想记时间就点时间块，想分析一件事才点事件反思。

> **R2 的一行旧代码都不改**：`ThingStore` / `ThingServiceImpl` / `RecordDothingPage` 全部保持原样。R2 只新增 `blocks` 一整套。这样没有迁移风险，旧数据零影响。

### 4.8 事件反思本身的后续微调（R3，可选）

现有 9 段全必填，对一个低频深度工具来说是合理的——你决定写的时候就该写完。但有两个真实问题：

1. **写不完。** 9 段长文中途被打断是常态，现在只能丢掉。→ 加 `status`（0 草稿 / 1 完成），允许中途存下。
2. **它和轻量复盘的关系没说明。** 三按钮是"每天扫一遍"，9 段是"挑一件事深挖"，两者是同一阶段（C 检查）的两个深度，不重复。
3. **写不完就永久丢了。** 事发当晚没有 30 分钟的写作能力，这是常态而非例外。
   → 目录加「一行事件」：20 字、不分类、存 `status=0` 草稿，日后展开时预填「客观简述」。
   细节见 `事件反思与行为模式-v0.1.md` §5.5 与 §13.1。

R3 做日复盘时一起处理，不进 R2。

## 5. 目标层

### 5.1 一个目标只有四样东西

名字、状态、一条下一步、当前标记。其余全部算出来。

### 5.2 详情页看三样，不看百分比

| 显示 | 来源 |
|---|---|
| 累计投入（多少小时） | `SUM(duration_min)` |
| 最后活动（几天前） | `MAX(occurred_at)` |
| 最近四周柱状（哪周空了） | 按周 `SUM` |

**永不显示"完成 63%"**。它要求人估，一估就假，而且要人每次更新。能自动算的三样已经足够回答"这条线还在不在动"。

### 5.3 「一条下一步」，不是任务列表

目标详情里只有一个输入框：`下一步做什么？`（一句话，可空，不排期、不勾选、不过期）。

做完了就替换掉。**这是任务的极限压缩形态**——比五条待办有用，因为它不会过期、不会累积、不会让你在列表里挑容易做的。

### 5.4 停滞与坟场

| 机制 | 实现 |
|---|---|
| 停滞判定 | `今天 - MAX(occurred_at) > 14 天` → 列表里折叠进「停滞」区 |
| **停滞是算出来的，不是状态** | 不新增 `status`，不在表里落"停滞"标记。你一动，它自动消失 |
| 坟场回顾（R4） | 每季度一次：「复活 / 改小 / 删掉」三选一 |

**为什么这是核心功能而非边角**：人同时想做的事有十个，实际能推进的只有两个。系统的价值不是让你把十个都推进，而是让你看清哪六个已经死了，然后心安理得地砍掉。砍掉比推进更值钱——砍完才有注意力。

### 5.5 活跃目标上限 3

建第 4 个"进行中"目标时，提示「已有 3 个在推进，暂停哪个？」。

这不是爹味，是防止用一个新目标逃避旧目标的烂尾。上限只在建的时候拦一次，不持续唠叨。

### 5.6 历史块的批量归属

R2 上线目标层之前如果已有块（当前 `things` 表里 R1 的旧反思），它们的 `goal_id` 为空。

目标详情页提供一次性操作：`把某时间段的块批量归入本目标`（选日期范围 → 确认）。只做一次，之后靠默认继承。

## 6. OPDCA：五个阶段，只有两个需要你动手

### 6.1 落点总表

| 阶段 | 系统里的形态 | 你的成本 | 版本 |
|---|---|---|---|
| **O 观察** | 时间块 + 记账，被动采集 | 1 次点击 | R2 |
| **P 计划** | 今天 3 件 + 各给预算时长 | 早上 3 次点选 | R4 |
| **D 执行** | 做就完了，R2.5 起有秒表/番茄可选 | 0 | R2 / R2.5 |
| **C 检查** | 日复盘三个按钮 + 计划 vs 实际 | 每条 1 次点选 | R3 |
| **A 改进** | 系统提议，你接受或否决 | 偶然 1 次 | R4 |

三层结构与 OPDCA 的对位：**目标层承载 P 的长期部分，计划层承载 P 的每日部分，块层同时是 O 和 D。**

### 6.2 O 与 D 是同一份数据

**这是整套系统的结构支点。** 你在"做"的时候，系统在"观察"——一个时间块既是执行证据，也是观察记录。

所以：不做两张表、不做两个页面、不做"待办完成后再补一条记录"。一份数据，两种读法。别人要你填两遍，你只填一遍。

### 6.3 P（计划）：每日 3 件 + 预算，达成率由系统算

**计划表**：`id` / `day`(`yyyy-MM-dd`) / `piece_code` / `target_min` / `note` / `created_at` / `updated_at` / `deleted`。

**录入**：早上打开录入页顶部的「今天做哪 3 件」，点 3 个片，预算默认沿用该片上次的值 → **3 次点击，0 打字**。

**达成判定：不手动勾选，全部自动算。**

```
actual    = 当天该片所有时间块的 duration_min 合计
rate      = actual / target_min
达成      = rate >= 0.8
部分达成  = 0.5 <= rate < 0.8
未达成    = rate < 0.5
```

按 `piece_code + day` 匹配，不要求绑到具体某条块——计划"写代码 2 小时"，实际分两次写了 100 分钟，也该算达成。

**为什么不做手动勾选**：勾选是一次额外动作，且人晚上回看时倾向"我觉得我做到了"。自动判定不可争辩，零成本。

### 6.4 C（检查）：三个按钮，不是九段作文

日复盘列表按时间倒序，每行：

```
写代码    90 分    [值得再来] [一般] [别做了]
短视频    40 分    [值得再来] [一般] [别做了]
```

点完即结束，**不写任何字**。只有点了「值得再来」，才弹出：「下次怎么做更快？一句话，可跳过」（`lesson`）。七个字就行。

**产出**：一年后你有几百条"值得再来" + 几百句一句话经验，而不是零篇作文。

**节奏**：日轻周重。日复盘只点按钮（1 分钟）；周日看一次汇总（时间去向 / 值得率 / 计划偏差 / 目标停滞）。

### 6.5 A（改进）：系统提议，不让你写计划

| 触发条件 | 系统的提议 |
|---|---|
| 某片连续 3 次「值得再来」 | "要不要把它设成每天固定 2 小时？" |
| 某片连续 3 次「别做了」 | "要不要从首选里收起它？" |
| 某片实际时长连续 3 次偏离预算 50%+ | "下次预算改成 90 分钟？" |
| 某 `lesson` 被同片引用 3 次以上 | "把这条设成该片的默认提示？" |
| 某目标停滞满 14 天 | "复活 / 改小 / 删掉？" |

每条提议都是**接受 / 忽略**两个按钮。忽略不追问、不重复弹。

**为什么这样设计**：Act 如果要你写"改进计划"，它就退化成了作文，和旧表单同归。把改进从"我该怎么做"变成"要不要采纳"，是唯一可能被长期使用的形态。

### 6.6 关于豆包方案的 Activity / Asset / Outcome

方向对（实体划分合理），落地错。三点修正：

| 它的实体 | 正确落法 | 错误落法 |
|---|---|---|
| Activity | 时间块，字段必须是**封闭集合**（片 + 时长） | 自由文本（= 又一篇文章） |
| Outcome | 复盘时的**一次三选一**，不在录入时 | 录入时填"产出是什么" |
| Asset | **一个查询**，不是一张表 | 独立 asset 表 + 必填栏 |

"写代码累计 300 小时、连续 20 周"这件事本身就是资产。做成表，用户就会为了填这一栏而**编造资产**——这是所有自我量化系统崩掉的头号原因。

（§5 的目标层就是 Asset 的正确落法：只有名字和一条下一步，其余全是查询。）

### 7.1 做

**R2「块 + 目标骨架」**（不含计时，**不改动事件反思**）

1. 时间块录入页（23 片 + 钉子 + 时长档），新增独立页面，**不动 `RecordDothingPage`**
2. 今日时间块列表（可编辑、可软删、可改目标归属）

5. 极简统计：今日/本周按片分钟数 + 占比 + **未记录**
6. 服务端：**新建 `blocks` 表**（`things` 一行不改）、新建 `goals` 表、`duration_min` 进统计口径

**R2.5「计时」**

7. 秒表（单实例 + 落盘恢复 + 异常标记）
8. 番茄节拍（25/45 + 到点本地通知 + 继续/结束）

**R3「C」检查**

9. 日复盘：三按钮 + 一句话

**R4「P + A」计划与提议**

11. 每日 3 件计划 + 预算时长 + 自动达成率

### 7.2 不做（含理由）

| 不做 | 理由 |
|---|---|
| 待办清单 / 任务列表 | 每条要命名、排期、勾选、会过期；过期就焦虑，焦虑就弃用。只保留 §5.3 的"一条下一步" |
| 目标的完成百分比 / 里程碑 / 子任务树 | 要人估，估算一假全盘皆假；引入层级就有规划成本 |
| 目标截止日期 | 没有超期失败，只看"还在不在动" |
| 甘特图 / 排期 | 一个人的项目不需要排期，需要"还在动" |
| 通知栏常驻计时 | 前台服务跨平台成本高，Windows 无对应物 |
| 多计时器并行 | 数据必脏，收益为零 |
| 计时暂停/继续 | 要存多段区间，改动面大，收益极小 |
| 番茄锁机 / 白噪音 / 专注模式 | 与"低成本记录"无关，是另一个产品 |
| 录入时采集 `mood` | 与 `worth` 重复 |
| 计划手动勾选完成 | 自动判定零成本且不可争辩 |
| 自动读手机 App 使用时长 | 隐私 + 系统权限 + 只能 Android，破坏口径一致 |
| 事情片的层级分类 | 一级 + 23 片已够，层级会让每次录入多一次决策 |
| 把事件反思并进时间块 | 粒度、读法、统计口径都不同，合表会污染两边（§4.7） |
| 提醒推送（除番茄到点外） | 通知是负担，会加速卸载；改为你打开时看到停滞 |
| 断签 / 连续打卡 / 惩罚机制 | 断签是放弃的头号原因 |
| 时间块重叠自动检测 | 复盘列表按时间排序，重叠肉眼可见 |
| 电脑端编辑时间块 | R1 已留 `updated_at`，界面留到后续 |

### 7.3 分期原则

**数据模型一次定型，功能分批上线。** 分期不是砍功能，是砍单次改动的面积：

- `blocks` 表在 R2 就把 `goal_id` / `worth` / `lesson` / `plan_id` / `anomaly` / `mood` / `started_at` / `ended_at` 全部建好，R2.5/R3/R4 只加界面和接口，不再动表结构和迁移。
- `goals` 表 R2 建全。
- `plans` 表 R4 再建（独立表，不影响 `blocks`）。
- `things` 表（事件反思）R2 **零改动**，包括它现有的必填校验——它不在这次改动面上。

- [ ] 新建目标后自动设为当前目标，之后录入的块自动挂上

与 `分析功能需求-v0.1.md` 一致，不另立口径：

- [ ] 一条块从录入到复盘，只需 1 次（录入）+ 1 次（复盘）点击
- [ ] 复盘一条 ≤ 1 次点击，全程可零文字完成

- [ ] 系统提议可以"忽略"，且忽略后不再重复弹出

## 17. 本地备份（2026-10-18 晚，已实现）

用户决定：**备份只存本地，不上云；数据导出暂缓**（后续要做 AI 接入时再考虑导出）。

### 17.1 为什么这是"必修"

服务端是唯一数据源，手机只缓存 30 天。文件损坏 / 误删 / 硬盘坏 = 不可逆；
而且手机在 30 天后会跟随镜像变成空。备份不是 nice-to-have。

### 17.2 实现

- `BackupService`：每天一份 `backups/personalhub-YYYY-MM-DD.db3`，用 **`VACUUM INTO`** 生成
  （库开着 WAL，直接复制文件会缺最近的事务且不报错）。
- `BackupWorker`（HostedService）：启动做一次 + 每 30 分钟检查"今天的在不在"，
  因为服务端常常连开好几天，只在启动时备份会漏掉后面每天的数据。
- 保留：最近 **14 天每天** + **每周日 12 份** + **每月 1 号 12 份**，其余自动清理。
  只删自己命名规则内的文件，绝不碰目录里别的东西。
- 目录默认 db 同目录 `backups/`，可用 `PERSONALHUB_BACKUP_DIR` 改；**不做任何云上传**。
- 失败处理：删除 0 字节半成品（一个空"备份"比没有更危险），记录 `LastError` 并在页面显示。

### 17.3 可见性（这条比功能本身重要）

- 新增 `/backup` 页：最近一份日期、份数、总占用、目录路径、每份的大小与各表条数、
  下载链接、「现在备份一份」按钮、以及三步恢复说明。
- 首页在"超过 2 天没生成"或"上次失败"时显示红字 + 跳转链接。**静默失败的备份等于没有备份。**
- 下载端点 `/backup/file/{name}` 只接受严格符合 `personalhub-YYYY-MM-DD.db3` 且确实在备份目录里的文件，
  其余一律 404（这个端口在局域网内无鉴权，不能变成任意文件读取）。

### 17.4 恢复：故意不做一键

恢复是"用旧文件覆盖全部数据"，一年用不到一次，点错一次就真没了。页面只给三步：
停服务 → 下载快照改名 `personalhub.db3` 覆盖（**同时删掉 `-wal` / `-shm`**）→ 启动。

### 17.5 后续（未做）

数据导出（JSON / CSV）暂缓；将来接 AI 时再决定导出形态。

## 18. R4 每日计划（2026-10-18 晚，已实现）

### 18.1 与目标的区别（这轮讨论的结论）

| | 目标（goals） | 计划（plans） |
|---|---|---|
| 时间尺度 | 季度级，可跨月 | **只有今天**，隔日作废 |
| 回答 | 我在推进哪条线、还动不动 | 今天想把时间给谁 |
| 数量 | 最多 3 个活跃 | 每天最多 3 件 |
| 怎么来 | 建时打一次字 | **0 打字，点选** |
| 失败后果 | 14 天没动折叠，不惩罚 | 达成率算出来，**不滚存** |
| 与块的关系 | 块挂 `goal_id`，是归属 | 按"片 + 当天"比对，**不绑具体块** |

一句话：**目标回答"为什么"，计划回答"今天先做哪个"。**
合并会同时毁掉两者：目标长出待办清单就会过期焦虑，计划承载长期第二天就作废。

### 18.2 数据与接口

- 新表 `plans`：`id / day(yyyy-MM-dd) / piece_code / budget_min / goal_id / created_at / updated_at / deleted`。
  **`day` 用字符串不存时间戳**：计划天然是"某一天"，存时间戳就得再回答一次"谁的时区、几点算跨天"，
  而时间块那边已有固定答案（UTC+8 自然日）。字符串让两边不可能对不上。
- 没有完成标记：达成率是当天同片时长 ÷ 预算现算的，**允许勾选就一定会有人忘了勾**，数字随即失真。
- proto 新增 `PlanService`（UploadPlans / ListPlans）。客户端 `LocalPlan` + `PlanUploader` + `RecordSyncService<LocalPlan>`，
  照现有四类记录再登记一套，旧代码零改动。

### 18.3 三条边界（实现里硬编码）

1. **一天最多 3 件**：第 4 件由服务端**拒绝**（`每天最多计划 3 件`），不是提醒。
   允许 5 件的那一刻它就变成待办清单。
2. **只点选**：加计划 = 选片 → 选预算档，两步全点选，没有输入框。
3. **不滚存、不催**：昨天没做完的不进今天；不推送，仅在录入页顶部显示。

### 18.4 界面

- 手机录入页顶部卡片：`今天做哪 3 件？` + `+ 加一件`；每行显示 `预算 X · 实际 Y` 与 `达成 / 部分 / 未达成`，
  右侧 `×` 去掉一件。实际时长随每记一笔块实时刷新。
- 达成度阈值：≥80% 达成 / 50~80% 部分 / <50% 未达成；预算 0 时只报实际。
- 管理端 `/blocks` 顶部新增「今天计划 vs 实际」（永远看今天，不受区间筛选影响）。

### 18.5 验证

探针新增 `r4` 模式，**10 项断言全过**：4 条只接受 3 条、第 4 条进 failed_ids、错误话说清上限、
当日 3 条、软删被接受、删一条后能补一条、墓碑不算数且默认不返回、非法日期被拒、区间查询可用。
管理端实测：写文档 45 分/预算 1 小时 → 部分；运动 0 → 未达成；吃饭 30/30 → 达成。

### 18.6 未做（按讨论留的）

- **系统提议**（A 阶段）：规则已定（某片连续 3 次"值得" / 3 次"别做了" / 实际连续偏离预算 50% / 连续 3 周有块但没进过计划 / 目标 14 天没动），
  但要等真实数据攒够 3 周才可能触发，本轮只把数据备齐（`worst`/`lesson`/`plans` 都在）。
- **季度坟场回顾**：目标的停滞折叠已有，季度回顾页（复活 / 改小 / 删掉）未做。

## 19. R5 行为模式 / 练习（2026-10-18 深夜，已实现）

### 19.1 两张表，两个频次

| | Pattern | Practice |
|---|---|---|
| 是什么 | 一个模式的拆解（触发 / 旧反应 / 新反应 / 保留的回报） | 一次"守住了"或"又回去了" |
| 频次 | 一季度 2~3 个 | 一天 0~1 次 |
| 成本 | 要写四段 | **1 次点击** |
| 表 | `patterns` | `practices` |

**为什么合成一张会坏**：前者低频高打字、后者高频零打字。这是第三次应用同一条原则
（时间块 vs 事件反思、目标 vs 计划）。

### 19.2 刻意没有的东西

- **没有成功率**：有比率就会开始不记失败那次，而"复发不是失败"是这条线的前提。
- **没有连续天数**：断一天就归零的计数器会让人直接放弃记录。
- **没有阶段字段**：TTM 阶段是**推断**出来的（次数 + 连续周），存在字段里两个月后必然过期。
- **没有情绪/强度/备注**：一天 0~1 次的动作用，多一个字段就少一半点击。

### 19.3 正向为主的按钮布局

失败有痕迹（有具体场景、好记），成功没痕迹（"守住了"是没发生的事，想不起来点）。
所以录入页里 **「守住了」是主按钮（绿、大、在左），「又回去了」是次按钮（灰、小、在右）**。
文案写明"只在想起来的时候点，不点不算失败"。

### 19.4 归因反查（这一层最值钱）

每次"又回去了"，在它**前后 3 小时**窗口里找时长最长的那个时间块，统计落在哪些片后面。
输出：`你标记「又回去了」的 12 次里，8 次紧挨着「开会」前后 3 小时。`
规则：**样本 < 10 次不下结论**（12 次里的 8 次会被当成规律，那是新的迷信）；少于 2 次命中也不说。

### 19.5 活跃上限 3

第 4 个由服务端拒绝。录入页最多显示 2 个（最近 14 天有练习的优先），
3 个模式 = 6 个按钮会吃掉首屏。

### 19.6 验证

探针 `r5` 模式 **14 项断言全过**：空名称 / 缺新反应被拒、3 个活跃建成、第 4 个被拒、
暂停后能建新的、列表 4 条、result=5 被拒、缺模式 id 被拒、两次练习入账、按模式查询、
软删后默认不返回。

**过程中发现并修掉一个真 bug**：`PatternStore` 在版本冲突时返回 `Success`，
导致"点了暂停、界面显示成功、服务端其实没改"。已改为与其他 Store 一致的"冲突即失败"。
这类错误不报错、不改数据，是最难发现的一种。

### 19.7 未做

管理端 `/patterns` 页（网页上还看不到模式与练习）、9 段事件反思保存后的「固化为模式」出口、
季度 Outcome 三档、TTM 的"提议已自动化"。

## 20. 激励机制边界（讨论结论，尚未实现）

用户带来豆包的"资产复利 + 解锁奖励"方案。结论：**方向可取，实体不可照搬。**

### 20.1 方案的根本问题：Asset 在本系统里不存在

豆包假设有 Activity / Asset / Outcome 三实体。本系统实际是：
时间块（Activity）/ 目标 / 计划 / 复盘评价（worth + lesson）/ 模式与练习。

"资产计数 +1、资产曲线"没有数据来源。如果为了让曲线动而新增"资产"记录，
它立刻变成第二个要维护的表 —— 与"打字预算与录入频次成反比"直接冲突。

### 20.2 采用：证据视图，而不是资产库

资产**不建表**，定义为查询结果：

| 证据 | 来源 | 已有 |
|---|---|---|
| 累计投入 | `SUM(duration_min)` by goal | ✅ |
| 方向 | 「值得」率 / 「别做了」次数 | ✅（值得在块上） |
| 节律 | 最近四周有记录的周数、目标最后活动 | ✅ |
| 性格证据 | Practice 次数与旧反应趋势 | ✅（R5） |

页面上叫「证据」，不叫「资产」。区别是：证据不需要你产出新记录，它只是把已经发生的聚起来。

### 20.3 外部奖励：可以做，但不做"解锁"

- **不做**：完成任务解锁奖励、积分、徽章、连续打卡——这些都会让动机变成"为了奖励"，
  且**必然诱导挑最容易达成的指标**（豆包的"资产占比 ≥30%"尤其容易被自我欺骗）。
- **可以做的唯一形态**：**预先承诺的休闲时间**。例如"连续 3 周每周 ≥8 小时写代码 → 周末半天不设任何记录"。
  奖励的是**节律**，不是成果；成果不该被贿赂。
- **明确不做惩罚**。理由不是道德，而是**数据可信度**：一旦有惩罚，你会开始不记坏的那天，整库就废了。

### 20.4 评价系统：三个数，不合成为一个分数

`投入`（小时）、`方向`（值得率）、`节律`（活跃周数）。
**绝不做单一总分**——一旦有总分，人会优化分数而不是生活。

### 20.5 落地顺序（未做）

1. 目标详情页把"值得率 / 活跃周数"补进三指标（纯计算，无新表）。
2. 季度回顾页：三个数 + 停滞目标的 复活 / 改小 / 删掉（R4 遗留的坟场回顾）。
3. 外部奖励只在季度回顾里手动勾"解锁"，不做自动判定。

## 21. 评价系统补齐：值得率 / 活跃周数 / 回顾页（2026-10-19 凌晨，已实现）

### 21.1 目标详情新增两个数

放在三指标下面单独一张小卡（不塞进原来的卡，避免一行四个数看不清）：

- **值得率** = 值得 ÷ 已评（最近 30 天）。没评过显示 `—`，**不显示 0%** —— 0% 会被读成
  "我做的事全都不值得"，而事实是"还没评"。
- **活跃周数** = 最近四周里有记录的那几周（`x / 4`）。
  比"累计 40 小时"更能说明这条线还在不在动。

两个都是现算，不存字段。

### 21.2 回顾页（`goal/review`）

入口：目标列表顶部「回顾：三个数 + 该砍的」。

1. **三个数**：投入 / 方向（值得率）/ 节律（活跃周 `x / 4`）。**刻意不合成一个总分** ——
   有总分就会开始优化分数，而不是生活。
2. **该砍的砍**：列出 14 天没动的目标，每个「处理」→ 改小 / 暂停 / 放弃。
   **没有"复活"按钮**：折叠是算出来的，记一笔它就会自己回来；给个按钮反而会让人
   以为"点一下就算继续在做了"。
3. **奖励自决**：三条预设奖励（半天空闲 / 一本书 / 短途出行），**手动勾选，按季度存本机**。
   文案写明：系统不判断你配不配；不做自动解锁，也不做惩罚。

### 21.3 口径的诚实标注

手机只有 30 天镜像，所以回顾页写的是"最近四周"，并在页面下方注明"季度全量统计后续放服务端"。
**宁可标注清楚，也不给一个看起来像季度、其实是四周的数。**

### 21.4 至此评价系统的全貌

| 层 | 内容 |
|---|---|
| 单条 | 值得 / 一般 / 别做了 + 一句话经验 |
| 每日 | 计划 vs 实际（达成 / 部分 / 未达成） |
| 目标 | 累计投入 · 最后活动 · 四周趋势 · **值得率** · **活跃周数** |
| 模式 | 守住次数 · 又回去次数 · 连续周 · 推断阶段 · 归因反查 |
| 回顾 | 三个数 · 停滞目标处理 · 奖励自决 |
| 横向 | 时间概览（去向 / 未记录 / 覆盖率）· 支出概览 |

## 22. R6 想法库（2026-10-20，已实现）

### 22.1 它解决的是哪一段

前面四类记录回答的都是"**已经发生**的事"：钱出去了、时间用掉了、这件事值得复盘、这一类反应要改。
想法不一样，它记的是**还没成形的东西**——可能三分钟后自己就否了，也可能一年后变成一条目标。

所以它在这套系统里的位置是**原材料仓库**：

```
想法（原材料） ──► 目标（加工后的行动产物） ──► 时间块（真正花掉的时间）
       └────────► 事件反思（挑重点深挖）
       └────────► 行为模式（高频"评价类"念头 → 矫正那一个反应）
```

本轮只做**第一段出口**：想法 → 目标。转成反思/模式先不做（那需要"一条想法配 9 段"，
会在录入时吓跑人；等想法库攒够量再决定怎么挑）。

### 22.2 类型：四种 + 未分类，**默认未分类**

| kind | 名称 | 判据（直接写在录入页上） |
|---|---|---|
| 0 | 未分类 | 先记下。以后想分再分，不选也不会丢任何东西 |
| 1 | 事实 | 发生了什么、能核对的东西 |
| 2 | 评价 | 好/坏、应该/不应该的判断 |
| 3 | 计划行动 | 打算做但还没做的事 |
| 4 | 脑补 | 想象、担忧、假设 |

**为什么不是必选**：分类是**事后整理**的动作，不是记录的动作。让用户在记的那一秒先想
"这算哪类"，就是在想法和数据库之间加了一道闸——而这道闸的成本，比它带来的整洁度高得多。
录入页把判据直接显示在 chip 下面，是因为光给四个词没人知道自己该点哪个；选错类型比不选更糟
（后面要靠"评价类"筛出该矫正的念头，喂错数据等于白做）。

### 22.3 刻意没有的东西（这是本模块最重要的一节）

1. **没有"处理状态"**。不做未处理/已处理/已归档。
   想法库不是待办清单：一旦有"未处理 37 条"，它就会变成第二个待办，
   然后开始有过期感，然后就不想打开它，然后就不记了。**攒着不发霉才叫库。**
2. **没有"自动生成目标"**。只能由用户点「转成目标」，而且点了之后是**预填到编辑框**、
   由人改写成一句能判断做没做完的话。原文往往带着情绪和背景
   （"我好像每次做完计划就松一口气，然后就不做了"），直接当目标名是无法验证的。
3. **没有去重**。同一个念头记两遍就记两遍。判断"这两条是不是一回事"需要语义理解，
   而误判合并会让用户**丢东西**——宁可重复，不可丢失。
4. **没有每日条数上限**（对比：计划每天最多 3 条）。想法没有"今天该有几个"的概念。
5. **没有提醒/催促**。想法库的价值在于"需要的时候能找到"，不在于"被处理完"。

### 22.4 交互约定

| 动作 | 落点 | 说明 |
|---|---|---|
| 记一条 | 记录目录 → 想法 → 大输入框 + 五个 chip | 保存后清空正文，**保留类型**（连着记同类是常见情况） |
| 看全文 | 点卡片正文 | 短的就地展开、长的弹半屏阅读卡（见 §23） |
| 转成目标 | 卡片右侧「转成目标」 | 预填 → 人改 → 建 LocalGoal → 想法回填 goal_id |
| 改类型 / 删除 | 卡片「⋯」 | 删除优先软删（墓碑），从未同步过的才物理删 |
| 浏览 | 想法库（筛选 + 最近 200 条） | 上限 200 条渲染，更早的去管理端看 |

`goal_id` 只做**标记**，不改正文、不改类型：转化不等于想法消失，
原文留着才能回头看"我当时是怎么想的"。

### 22.5 与"激励机制"的关系

想法库**完全不参与**任何得分、连续天数、完成率。它没有正向反馈，也不该有——
记一条想法不是"完成了什么"，它是给未来的自己留一份原材料。
一旦给想法加积分，人就会开始记"能得分的想法"，那这个库就废了。

## 23. 文字显示不全的统一处理（2026-10-20，已实现）

### 23.1 三种病，分开治

"字显示不全"不是一个问题，是三件不同的事：

| 病 | 表现 | 治法 |
|---|---|---|
| 布局病 | 该换行的没设 `WordWrap`、固定高度、`MaxLines` 太小 | **直接改布局让它不用点就能看全**（最优解） |
| 行内摘要 | 目标名 / 模式名 / 想法正文，结构上必须收紧才能扫读 | **点一下就地展开** |
| 长文本 | 几百上千字（反思、模式四段、想法） | **半屏阅读卡**，摊在列表里会把页面撑爆 |

### 23.2 为什么不用原生 ToolTip

MAUI 的 `ToolTipProperties.Text` 在 **Android 上是长按触发**（松手后几秒消失），
而本 App 的长按已经占给了「改时长 / 改名」菜单，直接撞车；
而且原生提示是小黑框、字多了照样截断。所以只能自绘。

### 23.3 自绘方案：TextPeek（两档，不做气泡）

- **≤100 字 → 就地展开**：放开 `MaxLines`、换 `WordWrap`，行自己长高，再点收回。
- **>100 字 → 半屏阅读卡**：屏幕中间浮一层，可滚动，点空白处/「知道了」关闭。

**为什么不是气泡**：手机没有 hover，气泡只能靠点/长按触发，而这两个手势都已经有主人；
而且气泡会压在手指下面，用户还得挪开手指才看得见。就地展开是"点完就在原地看"。

例外：**不能变高的位置**（统计条里定宽 96px 的片名列）用 `TextPeek.Attach(label, forceCard: true)`
永远走阅读卡，否则展开会把整行图表撑歪。

### 23.4 「点文字看全文」和「点行进详情」怎么共存

MAUI 对嵌套手势**没有统一的冒泡/捕获语义**，各平台实现不同，写死任何一个方向都会在某个平台错。
所以不猜顺序，改成**时间窗仲裁**（`TapArbiter`）：两个处理器都先 `TryClaim()`，
谁先到谁赢，后到的在 400ms 内被吞掉。行为与平台派发顺序无关。

### 23.5 文本框：替掉所有 `DisplayPromptAsync`

`DisplayPromptAsync` 在 Android 上是一个**单行小框**，几十个字只能看到尾巴，改旧内容等于盲改。
现在统一换成多行编辑器（`TextEditorPage`）两种形态：

- `compact: true` → 浮一层卡片：备注、下一步、改名字、改小、片改名
- `compact: false` → 整页编辑：模式四段（触发/旧反应/新反应/保留的回报）

短文本的位置（备注、下一步、目标名、事件标题、模式名）则直接从 `<Entry>` 换成
带 `AutoSize=TextChanges` 的 `<Editor>`（样式 `FieldEditor` + `FieldBorder`），
一行不够就自己长高，不再靠 `ClearButtonVisibility` 偷偷左右滚动。

## 24. 周回顾（2026-10-20，已实现）

### 24.1 它解决的是"感觉不到迭代"

这套系统原本的反馈周期是**一个季度**（目标回顾），而记录周期是**一天**。
中间那 89 天里系统不提供任何"你变了"的证据，于是人会觉得这个软件对自己没用 ——
**这不是 AI 不够聪明，是对比物不够近。**

周回顾把对比物缩短到 7 天：这周和上周并排放，四个数，看完十秒，不需要输入任何字。

### 24.2 四个数（刻意只有四个）

| # | 看什么 | 怎么算 |
|---|---|---|
| 1 | 投入 | 本周分钟 vs 上周分钟；变化量；留下了记录的天数 |
| 2 | 哪条线动了 | 每个进行中目标的本周/上周分钟；没动的显示"上次动是 N 天前" |
| 3 | 反复在说同一件事 | 最近两周所有 `lesson` 归一化后计数，出现 ≥2 次的上榜 |
| 4 | 时间挪到哪儿去了 | 按片对比本周与上周的分钟差，取 \|差\| ≥ 5 分钟的前 4 项 |

### 24.3 刻意没有的东西

1. **没有综合评分、完成率、连续天数**。同 §20：有分数就会开始优化分数。
2. **没有建议清单**。一旦给出建议，它就变成第三个待办列表。
3. **没有"退步"这个词**。第 4 项只陈述"少了 40 分钟"，不做价值判断 ——
   少记了可能是砍对了。
4. **没有一个输入框**。符合"需要用户维护的状态一律改算"。
5. **不显示百分比变化**（上周为 0 时）。除零得到的 ∞ 或 100% 都是假数字，
   这时候显示"新增"才是真的。

### 24.4 第 3 项的归一化边界（重要）

只做三件事：去空白、去标点、转小写。**不做同义词、不做语义相似度。**

另外补一条**前缀合并**：短句是长句前缀且长度差 ≤ 8 时视为同一句
（「先做25分钟」和「先做25分钟就好」是同一句话的两种写法）。

为什么不做得更聪明：一旦开始判断"这两句意思一样"，就会把不一样的句子合并，
而**合并错的代价是让人以为"我没改过"**，比不做更糟。

第 3 项其实是"AI 之前"最该由系统做的事 —— 它不需要理解语义，只需要数。
人看不见自己说了 12 遍同一句话，但计数看得见。

### 24.5 数据边界

手机只镜像最近 30 天，所以：
- 最多往前翻 3 周（`MaxBackWeeks = 3`），到头后按钮变成「回到本周」而不是灰掉
  （灰按钮会让人以为坏了）
- 第 1 项在翻到更早的周时，若本地无数据会显示"这一周没有记录"，
  但**这可能是本地被裁剪，不是真的没记** —— 页脚有明确提示。

## 25. 下一步 → 排进今天（2026-10-20，已实现）

### 25.1 为什么不是"点一下直接建时间块"

直接建块会在一天里造出两条并行路径：**有计划的块** 和 **临时加的块**。
月底统计分不清哪些是兑现的、哪些是临时起意，而"计划 vs 实际"正是 R4 存在的意义。

所以走**生成一条 `plans`**：
```
下一步 ──「排进今天」──► plans(今天) ──► 时间块页「今天计划」卡 ──► 点它记块
                                                                └─► 块自动带 GoalId + PlanId
```
完全复用 R4 已跑通的链路，**不新增表、不新增字段、不新增一套统计**。

### 25.2 排哪个片、多久：由历史推断

- **片**：这个目标最近 30 天用得最多的那个（次数优先，次数相同看总时长）
- **预算**：这个目标在这个片上的**中位时长**，再吸到最近的固定档（5/15/30/45/60/90/120/180）

用中位数不用平均数：平均会被一次马拉松拉飞，中位数不会。

**唯一会问用户一次的情况**：这个目标从来没记过时间块 —— 那是系统唯一没有依据的时刻。
问的也只是"做哪一类"，不是"写一句话"。

### 25.3 三道闸

| 闸 | 行为 |
|---|---|
| 今天已满 3 件 | 拒绝，提示"先去时间块页去掉一件"（不是静默失败） |
| 今天已排过同一个片 | 拒绝，提示"直接去点它就行"（同名两行会让人以为记错了） |
| 没有下一步 | 按钮禁用（半透明），点不动 |

### 25.4 还没做的：AI 提议下一步

用户反馈"很多时候确实不知道该写什么下一步"——这正是 AI 该介入的点。

但顺序必须是**先让系统能自己算，再让 AI 去算系统算不出来的**：

1. **规则版（不联网，先做）**：从历史里提候选
   - 最近在做的片 → "继续 {片}，{中位时长}"
   - 有一条 `lesson` → "按上次的经验：{lesson}"
   - 有"计划行动类"想法且未转目标 → 把那条想法搬过来
2. **LLM 版（需配置 key）**：把目标标题 + 最近 30 天片分布 + 最近 lesson + 想法喂进去，
   让它给 1~3 条**今天能做完、能判断做没做完**的下一步

硬约束（无论哪个版本）：
- 只**提议**，点一条才预填到输入框，永远不自动写入
- 不超过 3 条，不写解释段落，不评分、不催
- 输出必须是一句可验证的动作，不是"提升效率"这种没法判断的东西

## 26. 片级目标归属（2026-10-20，已实现）

### 26.1 原来的问题：归属是一个"全局单例"

旧逻辑：`GoalId = _activeGoals.FirstOrDefault(g => g.IsCurrent)?.Id`。
也就是说，**所有片、所有块，永远归到同一个"当前目标"**。

三条线同时推进时，只有一条能拿到归属，其余全部漏进第一条。
更糟的是它**看不出来**：保存后状态栏只写"已记下 写代码 30m"，不写归到哪。

### 26.2 现在的规则：三级优先

| 优先级 | 来源 | 生命周期 |
|---|---|---|
| 1 | 本页临时指定（点「归到目标」chip 选的） | 只在本页有效，退出即恢复自动 |
| 2 | **片记忆**：这个片上次归到哪个目标 | 长期，存本地偏好 |
| 3 | 当前目标（`IsCurrent`） | 长期 |

点一个片保存后，把它的实际归属写回片记忆 → **同一个片下次自动归对，不再需要任何操作**。

### 26.3 为什么存本地 JSON 而不是加表

它只是"默认值"，不是数据：

- 丢了不会丢任何记录（只是要重新点一次）
- 换手机不该需要同步它
- 本来 `PieceSettings` 就在用 `Preferences` 里的一份 JSON 存钉子 / 改名 / 隐藏 / 各片时长

所以直接在同一个 `State` 里加 `GoalFor: Dictionary<string,string>`。
旧版本的 JSON 没有这个键，`State` 的属性初始化器会补上；`Load()` 里再统一褓一次 null。

### 26.4 失效处理（最容易出错的地方）

片记忆指向的目标如果被**暂停 / 完成 / 删除**，`ResolveGoalId` 会：

1. 校验该 id 是否还在 `_activeGoals`（`Status == 0`）里
2. 不在 → **忽略记忆**，回退到当前目标
3. 不清除记忆本身 —— 目标恢复后记忆还活着，省得重新点一遍

这一条防的是"把新块写进一条死掉的目标里"——那种错误在统计里最难发现，
因为它不报错、数据也合法，只是归错了地方。

### 26.5 chip 的语义变了

| 状态 | 显示 | 含义 |
|---|---|---|
| 自动（默认） | `自动` | 每个片归它上次的目标；没记忆的归当前目标 |
| 临时指定 | `目标名`（蓝底白字） | 这一页接下来记的都归它 |
| 明确不归 | `不归目标` | 这一页接下来记的都不归任何线 |

点 chip 列出：`自动（每个片记上次的目标）` + 各个进行中目标 + `不归目标`。
**就地弹，不跳目标页**——跳页等于"改一次归属要离开录入页"，那样没人会改。

### 26.6 逃生口

长按片 → 「忘记归属（目标名）」→ 清掉这个片的记忆，下次回退到当前目标。
只在**有记忆时**才出现这一项，没记忆时点了没意义（不给假选项）。

### 26.7 刻意没做的（用户裁决 2026-10-20）

- **不做 6 秒撤销条**：如果归属本来就没记错，就不需要事后改。
- **不做震动反馈**：同上。

这一节记下来是因为它推翻了我原本的推荐。理由是成立的：
**撤销条解决的是"归错了"的补救，而片记忆解决的是"不会归错"本身。**
既然默认值已经对了，补救机制就是给一个不该发生的情况准备的成本。

## 27. AI 接入需求（2026-10-20，草案，待用户确认）

### 27.1 角色边界：助手 + 记录员，**不是教练**

| 角色 | 表现 | 要不要 |
|---|---|---|
| 助手 | 你点它才出现，做一件具体的事 | ✅ |
| 记录员 | 把你已经有的东西整理、归类、找重复 | ✅ |
| 教练 | 主动指出问题、给建议、打分、催 | ❌ |

不做教练的理由：
1. 会制造"被评估"的压力，人开始为 AI 表演而不是为自己记录
2. 给建议清单 = 制造第三个待办列表
3. 建议一旦错一次，信任就没了，然后整个功能被放弃

### 27.2 该做的三件事（按价值排序）

**A. 提议下一步（最刚需）**

现状：目标详情页的「下一步」是一个输入框，用户常常不知道该写什么。

输入（发给模型）：
- 目标标题
- 该目标最近 30 天用过的片（次数 + 总时长）
- 最近 5 条 `lesson`
- 最近 10 条未转目标的「计划行动类」想法
- 上一次的下一步（如果有，说明没做完）

输出（强制 JSON）：
```json
{ "options": [
    { "action": "读第 6 章并写 3 条笔记", "piece": "reading", "minutes": 25 }
] }
```

约束：
- 1~3 条，`action` ≤ 20 字，必须是"今天能做完、能判断做没做完"的动作
- `piece` 必须是**已存在**的片 code（否则用户不知道点哪个）
- `minutes` 必须是固定档之一（5/15/30/45/60/90/120/180）
- 不写理由（理由会让人想辩论，而辩论不产生行动）

交互：点一条 → 预填到「下一步」输入框 → 人改 → 保存 → 再点「排进今天」。
**永远不自动写入。**

**B. 把反复出现的评价类想法归成一类，提议一个行为模式**

前提：想法库里「评价类」攒够量。靠计数找出高频词/高频句型，再由模型提一个新反应。
风险：误判会让人反感（"我根本不是这个意思"）。

**C. 周回顾的一句「最大差别」**

系统已经能算四个数（§24），AI 只补一句话。
风险：它会编。数据不够时宁可不说。

### 27.3 A 的工程细节

- **Key 只在服务端**：`PH_LLM_KEY` 环境变量 / `appsettings.json`。客户端不接触 key（会被反编译）。
- **客户端 → gRPC → 服务端 → DeepSeek**：复用现有链路。
- **只在用户点「帮我想」时调用**，绝不后台跑。
- **同目标同一天最多生成 1 次**，结果缓存在本地偏好里（反复点不重复烧 token）。
- **超时 15 秒**，超时/无网 → 直接降级到规则版，不弹错误。
- **返回不合规 JSON** → 重试 1 次 → 仍失败用规则版。
- **规则版永远可用**（不联网）：
  - 继续上次那个片 + 中位时长
  - 按上次 lesson 做
  - 把「计划行动类」想法搬过来

### 27.4 待确认的问题

1. 触发方式：只在你点的时候出现，还是也允许打开 App 时主动提一句？
2. 能接受把「目标标题 + 片使用 + lesson」发给 DeepSeek 吗？
3. 除了"帮我想下一步"，B / C 要不要排进去？
4. Key 你自己写进服务端配置，还是要一个管理端页面来填？
5. 用 `deepseek-chat` 还是 `deepseek-reasoner`？（这个任务建议 chat：快、便宜，不需要推理链）
