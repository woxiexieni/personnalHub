## 0. 一句话定位

**把每天的行为，变成可以复利的资产。**

拆成两个可验收的条件：

1. **记录一次的成本，要低到你会一直做**（否则样本不够，复利无从谈起）；
2. **回顾一次的产出，要具体到能改下一次的行为**（否则只是把数据搬了个地方）。

这两条是后面所有取舍的裁判：任何功能如果不同时服务其中一条，就不进 v0.2。

## 1. 复利闭环：五步，缺一步就断

| 步骤 | 要什么 | 现状 |
|---|---|---|
| 1 记录 | 10 秒内完成；离线可记；类型可扩展 | 部分（只有支出 + 事件反思，且入口平铺） |
| 2 可信 | 口径统一；**记错了能改**；能删 | **几乎没有**（无编辑、无删除、无管理端） |
| 3 回顾 | 固定的回看节奏（日/周/月） | 只有"今日列表" |
| 4 结论 | 不只给数字，要给"哪类涨了""哪件事反复发生" | 无 |
| 5 复用 | 上次的"行动计划"下次能被检索到、能标记做到没做到 | 无（`action_plan` 字段存了，但从不回流） |

**你的初衷"复利"，卡在第 2 步。** 只要一天不能方便地改错，数据就不可信，后面三步全是在脏数据上做乘法。所以这轮的重点不是"加图表"，而是**先把写路径补完整**（改、删、补录、收入）。

第 5 步是你这个软件真正的护城河——记账 App 都有第 1~4 步，但没有"上次我说要怎么做，这次做到了吗"这一层。它值得单独设计，但不在这轮。

## 2. 信息架构：底部只留两项

### 2.1 为什么是两项

底部 Tab 是**任务导向**的，不是**类型导向**的。类型会持续增加（支出、收入、事件反思、习惯打卡、体重、阅读、待办……），底部永远加不完。所以：

- **概览** = 读：所有数据的汇总展示
- **记录** = 写：一个目录，点进去才是具体录入

### 2.2 概览页（原"主界面"改造成数据界面）

从上到下：

1. **本月三数**：支出 / 收入 / 结余（收入确认要记之后，这三个数才有意义）
2. **今日**：今日支出 + 笔数（一句话："今天花了 ¥86.5，记了 4 笔"）
3. **分类占比**：本月支出构成（直接复用统计接口，不单独取数）
4. **最近 5 条**：金额、分类、时间、同步状态
5. **事件反思**：本周记录几条 + 最近一条标题（点击进详情）
6. **同步状态条**：最后同步时间 / 待同步条数 / 失败重试

### 2.3 记录页（目录）

一行一个类型，右侧显示"最近一次：今天 12:30"或"还没记过"：

| 类型 | 状态 | 说明 |
|---|---|---|
| 支出 | 已有 | 金额 / 分类 / 支付方式 / 时间 / 备注 |
| 收入 | 本轮新增 | 金额 / 收入分类 / 时间 / 备注 |
| 事件反思 | 已有 | 10 字段长文本 |
| 习惯打卡 / 体重 / 阅读 / 待办 | 预留 | 未来加，只需注册一行 |

**实现上的关键**：这不是"写死三个按钮"，而是一张**类型注册表**（名称、图标、路由、对应服务端表/接口）。加新类型 = 注册表加一行 + 写一个录入页，不动导航结构。这是"可扩展"落到实处的样子。

## 3. 收入：确认要记

### 3.1 数据

`records` 增加 `direction`：

```
0 = 支出（默认，老数据不用迁移）
1 = 收入
```

### 3.2 分类 id 分段（避免两套分类撞号）

- 支出分类：`1 ~ 99`（沿用现有餐饮 1、交通 2、购物 3、居住 4、娱乐 5、医疗 6、其他 7）
- 收入分类：`101 ~ 199`（工资 101、奖金 102、理财收益 103、退款 104、其他 105）

好处：一个 `category_id` 就能判断方向，不用在两张表之间来回查；历史数据一个字节都不用改。

### 3.3 录入交互

录入页顶部加**两段切换**「支出 / 收入」，切过去之后分类 Picker 换成对应分类集合。其余字段不变（收入不显示"支付方式"，改成"到账账户"可选，v0.2 先不做）。

### 3.4 统计口径

- **结构分析只看支出**（`direction = 0`）。
- 概览页的"结余"= 本月收入 − 本月支出。结余为负时按支出处理，用红色（你的中国习惯：涨红跌绿，这里"负结余"是坏消息，用红）。
- 收入不计入"日均支出"。

## 4. 电脑端管理界面（本轮新增）

### 4.1 为什么必须有

手机端改错是反人类的：列表小、没有搜索、没有批量、误触风险高。而录入错误是**必然事件**，不是意外。改不了 → 数据不可信 → 复利断在第 2 步。

所以管理端不是"顺便做的后台"，它是**数据可信度的兜底设施**。

### 4.2 范围（v0.2）

| 功能 | 说明 | 优先级 |
|---|---|---|
| 账单列表 | 按日期区间 / 分类 / 方向 / 支付方式筛选；备注搜索；分页 | P0 |
| 编辑 | 金额、分类、支付方式、消费时间、备注 | P0 |
| 删除 | 软删除（可恢复），不是真删 | P0 |
| 补录 | 电脑上直接加一笔（补昨天的） | P0 |
| 分类维护 | 增删改、排序、停用（停用不影响历史统计） | P1 |
| 数据体检 | 未分类、金额异常、未来时间、超长未同步的记录列表 | P1 |
| 导出 CSV | 备份与外部分析 | P2 |
| 事件反思浏览 | 只读列表 + 详情（编辑留到 v0.3） | P2 |

### 4.3 形态选型（需要你定，见第 8 节）

**方案 A：WinForms 桌面窗口**，直接读写 SQLite
- 优点：双击 exe 就有窗口，无浏览器；桌面感强
- 缺点：只能坐在电脑前；UI 迭代慢；和 gRPC 宿主共存要改程序结构（`OutputType` / 消息循环）

**方案 B：本地网页**（Razor Pages 或 Blazor Server，挂在现有 ASP.NET Core 上）
- 优点：**不改宿主结构**（你已经有 `WebApplication`，加几行 `MapRazorPages` 即可）；手机连同一 Wi-Fi 也能打开（临时躺床上改一笔）；UI 现代；将来想远程访问只差一个端口映射
- 缺点：要开浏览器

**我推荐 B**，核心理由是"手机也能临时打开"这一条——你迟早会遇到"人不在电脑前但要改一笔"的场景，而 A 方案到那天要重写一遍。

### 4.4 一条硬约束：管理端不绕过校验

管理端和手机端必须走**同一套 Store / Service 方法**（不直接拼 SQL 改库）。否则会出现"手机上不让存金额 0，电脑上能存进去"，统计立刻算错。

## 5. 编辑与删除：同步语义（最容易埋 bug 的地方）

### 5.1 现状

手机只增不改，服务端按 id upsert，删除能力根本不存在。所以"电脑端改了数据，手机本地那份怎么办"这个问题，以前不存在，现在**必须回答**。

### 5.2 三种方案

| 方案 | 做法 | 代价 | 风险 |
|---|---|---|---|
| A 双向同步 | 服务端记 `updated_at` / `deleted_at`，手机按增量拉取覆盖本地 | 大（增量协议 + 冲突解决） | 冲突规则复杂，容易丢数据 |
| **B 手机不存历史** | 手机只缓存**今日明细 + 未同步记录**，历史一律向服务端查 | 小 | 无网时看不到历史（可接受） |
| C 不传播 | 电脑端改动只在服务端生效，手机只看统计 | 最小 | 明细对不上，用户会怀疑数据 |

**推荐 B**，而且它与你原有的原则一致：「手机端不保存完整历史数据」（这一点写在最早的方案文档里，不是新决定）。

### 5.3 B 方案的落地规则

1. `records` / `things` 增加 `updated_at`、`deleted`（0/1）。
2. 所有查询默认过滤 `deleted = 1`。
3. **手机端合并规则**（唯一需要小心的地方）：
   - 本地 `Synced = false` 的记录：**永远以本地为准**（用户刚记的不能丢，也不允许被服务端覆盖）。
   - 本地 `Synced = true` 的记录：以服务端返回为准（服务端删了 → 本地删；服务端改了金额 → 本地更新）。
4. 手机拉"今日列表"时顺带完成这个覆盖，不需要额外的同步接口。
5. 删除一律软删（`deleted = 1`），管理端提供"回收站"（P2）。理由：误删账单比误改更常见，硬删无法挽回。

## 6. 需求边界（v0.2 明确不做）

写清楚"不做"，比写清楚"做"更能防止项目失控：

- 多用户、登录、权限
- 公网部署 / 云端同步（仅局域网）
- 手机端编辑历史记录（手机只补录 + 查看，改错去电脑）
- 图片 / 附件 / 语音录入
- 预算、预测、超支提醒（v0.3）
- 同比、自定义日期区间
- 事件反思的 AI 总结（先有结构化数据，再谈智能）
- 多币种

## 7. 分期（建议顺序，理由见下）

| 轮次 | 内容 |
|---|---|
| **R1（本轮）** | 数据地基：`categories` 表 + `direction` + `updated_at`/`deleted` + 索引；收入录入；概览页 + 记录目录（导航重构）；电脑端管理界面（账单增删改查 + 补录） |
| R2 | 支出结构统计页（`分析功能需求-v0.1.md` 的全部内容） |
| R3 | 周/月回顾、预算与预测 |
| R4 | 事件反思分析 + 行动计划跟踪（复利闭环第 5 步） |

**为什么把统计页从"第一"挪到"第二"**：统计页依赖分类表和收入字段，这两样本来就在 R1 里；而管理端依赖的软删除也属于同一批 schema 改动。**一次改表，两件事都落地**，比改两次表便宜。而统计页可以晚两周做，数据地基晚两周做就要迁移两次。

如果你更想先看到图表，也可以把 R2 提到前面——但那样 R1 的 schema 要先做完（它本来就是前置条件）。

## 8. 决策记录（2026-10-18 全部确认）

| # | 决策点 | 结论 |
|---|---|---|
| 1 | 管理端形态 | **B 本地网页**（挂在现有 ASP.NET Core，手机可临时打开） |
| 2 | 手机端是否存历史 | **不存**。只缓存今日明细 + 未同步记录；存储与分析全部在服务端 |
| 3 | 删除方式 | **软删**（`deleted = 1`），管理端提供回收站 |
| 4 | 本轮顺序 | 按第 7 节 **R1** 走：先数据地基 + 管理端，再统计页 |

由此确定的两条实现约束：

- 手机端不再承担"历史数据容器"的角色，任何"翻历史"的需求都必须走服务端接口（离线时明确降级，不假装有数据）。
- 服务端是唯一真相来源（single source of truth），管理端与手机端共用同一套 Store/Service 校验。
