## 0. 一句话定位

**把每天的行为，变成可以复利的资产。**

拆成两个可验收的条件：

1. **记录一次的成本低到你会一直做**（否则样本不够，复利没有本金）；
2. **回顾一次的产出具体到能改下一次的行为**（否则只是换个地方存数据）。

这两条是后面所有取舍的裁判：任何功能如果不同时服务其中一条，就不进 v0.3。

---

## 1. 复利闭环：五步，缺一步就断

| 步骤 | 要什么 | 现状 |
|---|---|---|
| 1 记录 | 能离线记；类型可扩展 | 部分（只有支出 + 事件反思，入口平铺） |
| 2 可信 | 口径统一；**记错了能改**；能删 | **几乎没有**（无编辑、无删除、无管理端） |
| 3 回顾 | 固定的回看节奏（日/周/月） | 只有"今日列表" |
| 4 结论 | 不只给数字，要给"哪类涨了""哪件事反复发生" | 无 |
| 5 复用 | 上次的"行动计划"下次能被检索到、能标记做到没做到 | 无（`action_plan` 存了但从不回流） |

**卡在第 2 步。** 只要一天不能方便改错，数据就不可信，后面三步都是在脏数据上做乘法。所以本轮重点不是"加图表"，而是**把写路径补完整**（改、删、补录、收入）。

## 2. 信息架构：底部只留两项

### 2.1 为什么是两项

底部 Tab 是**任务导向**的，不是**类型导向**的。类型会持续增加（支出、收入、事件反思、习惯、体重、阅读……），底部永远加不完。所以：

- **概览** = 读：所有数据的汇总
- **记录** = 写：一个目录，点进去才是具体录入

### 2.2 概览页

1. **本月三数**：支出 / 收入 / 结余
2. **今日**：今日支出 + 笔数（"今天花了 ¥86.5，记了 4 笔"）
3. **分类占比**：本月支出构成
4. **最近 5 条**：金额、分类、时间、同步状态
5. **事件反思**：本周几条 + 最近一条标题
6. **同步状态条**：最后同步时间 / 待同步条数 / 失败重试

### 2.3 记录页（目录）

一行一个类型，右侧显示"最近一次：今天 12:30"或"还没记过"：

| 类型 | 状态 |
|---|---|
| 支出 | 已有 |
| 收入 | 本轮新增 |
| 事件反思 | 已有 |
| 习惯 / 体重 / 阅读 / 待办 | 预留 |

**实现关键**：这不是"写死三个按钮"，而是一张**类型注册表**（名称、图标、路由、服务端表/接口）。加类型 = 注册表加一行 + 一个录入页，不动导航。

## 3. 收入：确认要记

### 3.1 数据

`records` 增加 `direction`：`0 = 支出`（默认，老数据零迁移）、`1 = 收入`。

### 3.2 分类 id 分段（两套分类不撞号）

- 支出：`1 ~ 99`（餐饮 1、交通 2、购物 3、居住 4、娱乐 5、医疗 6、其他 7）
- 收入：`101 ~ 199`（工资 101、奖金 102、理财 103、退款 104、其他 105）

一个 `category_id` 就能判断方向，不用两表互查。

### 3.3 统计口径

- 结构分析只看支出（`direction = 0`）
- 结余 = 本月收入 − 本月支出；为负时用红（中国习惯：坏消息用红）
- 收入不计入"日均支出"

## 4. 录入页（v0.3 定稿）

### 4.1 结论先行：不做"10 秒录入"竞赛

你明确说了"10 秒录入没那么重要，我只要数据"。这句话很关键，它砍掉了一批看起来聪明、实际上要额外数据积累才成立的功能。**本版明确不做**：

| 砍掉 | 为什么不做 |
|---|---|
| 常用组合一键记（"午饭 25 餐饮 微信"） | 要先积累几十条数据才能算出"常用"；冷启动期完全无效，是典型的花架子 |
| 金额算式输入（`12.5+8`） | 容易误触；真想算，手里有计算器 |
| 分类按使用频次动态排序 | 顺序会跳动 → 你会找不着东西。**固定顺序 = 位置记忆稳定**，长期反而更快 |
| 保存后 3 秒倒计时撤销 toast | 要处理页面切走、连续保存、竞态，代码不简单；改成"列表内编辑/删除"后完全不需要（见 4.4） |

### 4.2 保留的调整（成本低、收益确定）

1. **金额置顶**：现在在第 4 位，要滑下去再滑回来
2. **分类从 Picker 改成 chips**：不是为了省 2 秒，是因为全屏模态框选错了更难退出，且代码更绕
3. **时间折叠成一行，默认"现在"**：最不需要改的字段不该占一个表单项
4. **保存后不跳页，清空金额和备注**：连着记几笔很常见
5. **顶部常驻「今日总额」**（见 4.3）

### 4.3 今日总额：本地先算，服务端校正

**要求**：未同步也要看到今天花了多少。

一次网络请求的往返是 100~500ms，甚至可能失败。等它回来才显示数字，等于把"记完立刻有反馈"这件事交给了网络。所以分两层：

| 层 | 数据源 | 特点 |
|---|---|---|
| **即时值** | 本地 SQLite `SUM(amount)` where `direction=0` and `spent_at ∈ 今天` and `deleted=0` | 0ms，含未同步，离线可用 |
| **校正值** | 服务端 `GetTodaySummary` | 含电脑端补录、其他来源；返回后覆盖显示 |

实现要点：
- 进页面时先渲染即时值，再发一次校正请求（静默，不 loading、不闪烁）
- 保存成功后立即重算即时值（不等网络），同时排一次校正
- 两者不一致时**直接以服务端为准刷新**，不弹窗。差异只可能来自电脑端补录 —— 用户自己刚做过的事，不需要解释
- 口径必须与统计一致：**固定 UTC+8、`[今日 00:00, 次日 00:00)` 左闭右开、整数分累加**。这条不统一，本地和服务端会永远差一笔
- 显示格式：`今天 ¥86.50` + 小字 `4 笔 · 2 笔待同步`

**边界规则（防止口径分叉）**：
> 本地数据**只**服务「今日总额」和「今日列表」。概览页的分类占比、月汇总一律走服务端接口。
> 理由：30 天缓存装不下"本月"以外的口径，一旦允许本地算统计，就会出现"手机说 3200、网页说 3100"。

### 4.4 撤销与修改：列表内 CRUD，不做倒计时 toast

你的原话是"未同步前可以有一个撤销操作对消费单项进行撤销修改"。这比"3 秒 toast"更好实现也更可靠：

**今日列表每行**：金额 · 分类 · 时间 · 同步状态点 · `[编辑]` `[删除]`

| 记录状态 | 能否编辑 | 能否删除 | 删除的实际行为 |
|---|---|---|---|
| 未同步（`Synced=0`） | 可以 | 可以 | 本地物理删（服务端根本没有这条，删干净最省事） |
| 已同步·今天 | 允许 | 允许 | 本地标 `deleted=1` + `Synced=0` → 上传时服务端软删 |
| 已同步·昨天及更早 | 只读 | 不允许（去电脑删） | — |

编辑后一律 `Synced=0`，重新上传时按同一 `Id` upsert 覆盖服务端。因为客户端时间必然最新（就是你刚改的），不需要额外的版本号比较；单用户局域网场景不存在并发写冲突。

**为什么"今日已同步"也放开（已确认）**：自动同步很快，你记完 1 分钟就同步完了，5 分钟后发现金额打错 —— 按"已同步就不能改"的规则就得开电脑，这会让"改错必须开电脑"覆盖掉 95% 的真实场景。放开"今日已同步"后，改错的摩擦降到接近零，而代价只是多一条软删上传路径（本来也要为管理端实现）。

**判定"今天"必须用固定 UTC+8，不用设备时区**。否则设备时区不是东八区时，手机上"今天能改"和服务端"今天"不是同一天。这条与统计口径共用同一个日界函数（见实现方案 `LocalDay`）。

## 5. 手机端缓存策略：最近 30 天

### 5.1 决策变更说明

v0.2 定的是"手机不存历史，只缓存今日 + 未同步"。你这次要求"留一个月、慢慢删"，所以改为：

> **本地保留最近 30 个自然日的已同步记录 + 全部未同步记录。**

这不影响"服务端是唯一真相"这条原则 —— 本地那 30 天只是**可丢弃的副本**，任何时候删掉都能从服务端重建。

### 5.2 数据量

一天 10 笔 × 30 天 = 300 行，SQLite 不到 1 MB。**容量不是问题，所以清理策略可以很笨、很简单**，不需要做增量优化。

### 5.3 清理规则（最容易写错的地方）

```
删除条件：Synced = 1 AND spent_at < 今天-30天
永不删除：Synced = 0（无论多老）
```

实现上有三个坑：

1. **只删本地副本，绝不调服务端的删除接口**。方法名建议叫 `PruneLocalCache()` 而不是 `DeleteRecords()` —— 命名错了，三个月后一定会有人把它接成真的删除。
2. **清理放在同步成功之后 / App 启动时，后台跑**。不要塞进保存按钮的路径里，否则保存会莫名卡一下。
3. **未同步的行即使超过 30 天也要留着**（比如你出差两周没连上服务端）。先删老数据再判断未同步，就会把唯一一份数据删掉 —— 这是真正会丢数据的场景。

### 5.4 合并规则（拉 30 天做镜像覆盖）

不写增量同步协议。一个月账单最多几百条（< 100 KB），**全量拉回来做覆盖**，简单且自愈：

```
1. 请求 ListRecords(今天-30天, 明天)   → 服务端返回窗口内全部记录（含 deleted 标记）
2. 窗口内 Synced=1 的本地行：以服务端结果为准（服务端改了金额就更新，服务端没这条就删本地）
3. 窗口内 Synced=0 的本地行：原样保留，不被覆盖、不被删除
4. PruneLocalCache()
```

幂等：重复执行结果一致。本地数据库被改脏了（比如从旧版本升级），一次同步就修回来。

### 5.5 离线时的行为

- 今日总额、今日列表：正常显示（本地有）
- 最近 30 天明细：正常显示（本地有）
- 30 天以外、分类占比、月汇总：明确显示"需要连接服务端"，**不显示缓存假数字**

## 6. 电脑端管理界面（本地网页）

### 6.1 为什么必须有

手机改错是反人类的：列表小、没搜索、没批量、误触风险高。而录入错误是**必然事件**。改不了 → 数据不可信 → 复利断在第 2 步。它是**数据可信度的兜底设施**，不是"顺便做的后台"。

### 6.2 范围

| 功能 | 说明 | 优先级 |
|---|---|---|
| 账单列表 | 日期区间 / 分类 / 方向 / 支付方式筛选；备注搜索；分页 | P0 |
| 编辑 | 金额、分类、支付方式、消费时间、备注 | P0 |
| 删除 | 软删（可恢复） | P0 |
| 补录 | 直接加一笔（补昨天的） | P0 |
| 分类维护 | 增删改、排序、停用（不影响历史统计） | P1 |
| 数据体检 | 未分类、金额异常、未来时间、超长未同步 | P1 |
| 导出 CSV | 备份与外部分析 | P2 |
| 事件反思浏览 | 只读列表 + 详情 | P2 |

### 6.3 形态：本地网页（已确认）

挂现有 ASP.NET Core（`MapRazorPages`），手机连同一 Wi-Fi 也能开。选它不是为了好看，是为了"人不在电脑前但要改一笔"那天不用重写。

### 6.4 硬约束：不绕过校验

管理端与手机端走**同一套 Store / Service 方法**，不直接拼 SQL。否则会出现"手机不让存金额 0，电脑能存进去"，统计立刻算错。

## 7. 删除：软删

- `records` / `things` 增加 `updated_at`、`deleted`（0/1）
- 所有查询默认过滤 `deleted = 1`
- 手机端删除已同步记录 = 本地标 `deleted=1` + `Synced=0`，随下次上传生效
- 回收站在管理端（P2）；手机端不提供恢复（手机上删的都是缓存副本，服务端才是真相）
