## 1. 要回答的问题（用户故事）

打开 App，不看明细，只想知道四件事：

1. **这个月我花了多少？** —— 一个数字，加一句"比上月同期多/少 x%"。
2. **钱主要花在哪？** —— 分类占比，从大到小排，一眼看出前三名。
3. **哪一类变多了？** —— 每个分类带环比，找出"悄悄涨上去"的那一项。
4. **我用哪个渠道付得最多？** —— 支付方式构成（次要，放页面下半部分）。

验收这句话是否成立的标准：**用户看完这一页，能说出"我该少花哪一类"**。说不出来，说明只做了数字搬运。

## 3. 指标口径（这一节比代码重要）

口径不定死，后面每一张图都会打架。以下全部**在服务端计算**，客户端只传档位标识，不传时间范围——避免手机和电脑各算一遍、得出两个数。

### 3.1 时间归属

- 一律按 `spent_at`（消费时间），**不按 created_at**。
- 时区固定 **UTC+8（Asia/Shanghai）**，不跟随服务器机器时区。否则换一台云服务器，"今天"就变了。
- 边界：左闭右开 `[start, end)`。`23:59:59.999` 属于当天，`00:00:00.000` 属于次日。

| 档位 | 起点 | 终点 |
|---|---|---|
| 今日 | 本地 00:00 | 次日 00:00 |
| 本周 | **周一** 00:00（中国习惯，非周日） | 下周一 00:00 |
| 本月 | 1 日 00:00 | 次月 1 日 00:00 |
| 本年 | 1 月 1 日 00:00 | 次年 1 月 1 日 00:00 |

### 3.2 币种与精度

- 第一版只支持人民币，不做多币种。
- `amount` 用 `double` 传输（与现有 proto 一致），但**服务端聚合用整数分**（`long` 分）累加，只在输出时除以 100。原因：`0.1+0.2` 的浮点误差会在"占比加起来不等于 100%"上暴露。
- 展示保留 2 位小数。

### 3.3 分类归属

- 以 `category_id` 聚合，服务端返回时**补齐 name/icon**。
- `category_id` 在分类表里查不到（历史脏数据、分类被删）→ 归入「未分类」，**不允许丢弃**。
- 占比分母 = 区间内**全部支出**，不是"已分类合计"。这样各分类占比一定加起来 100%。

### 3.4 排名

- 按金额降序；金额相同时按 `category_id` 升序。保证同样数据每次返回顺序一致（否则列表会随机跳动）。

### 3.5 环比

- 对比"上一周期同期"，不是"上一个完整月"。
  - 本月 = 10-01 ~ 10-18 → 对比 09-01 ~ 09-18，而不是整个 9 月。
  - 理由：月初拿 3 天和整月比，永远显示"暴跌 90%"，毫无意义。
- 上一周期无数据（`prev = 0`）时：`delta_ratio` 返回 0，同时把 `has_prev` 置 false，客户端显示"—"而不是"↑100%"。

### 3.6 收入

- **已确认要记收入**（见 `产品需求总览-v0.2.md` 第 3 节）。
- `records` 增加 `direction`（0 = 支出，1 = 收入）；**结构分析只统计 `direction = 0`**。
- 收入只影响概览页的"结余"（收入 − 支出），不计入日均支出、不计入分类占比。
- 收入分类 id 使用 `101 ~ 199` 段，与支出分类（1~99）不重叠，方便用一个字段判方向。

## 4. 数据模型改造

### 4.1 新增 `categories` 表

| 字段 | 说明 |
|---|---|
| id | 与客户端 `category_id` 对齐，1~7 沿用现有编号 |
| name / icon | 展示用 |
| sort_order | 页面自定义排序 |
| enabled | 停用后不再下发，但历史数据仍可统计 |
| updated_at | 客户端判断是否需要更新模板 |

配套实现 `CategoryService.GetCategories`（proto 里早就有，服务端一直没实现），客户端 Picker 改为从服务端拉取、本地缓存一份。

### 4.2 `records` 增加 `direction`（必做）

```
0 = 支出（默认，老数据不用迁移）
1 = 收入
```

配套：收入分类 id 用 `101 ~ 199` 段；结构分析一律 `WHERE direction = 0`。

### 4.3 `pay_method` 收敛

现在是自由文本，`"微信"`/`"微信支付"`/`"wx"` 会被算成三笔。方案：

- 服务端下发受控列表（沿用现有 4 项：微信 / 支付宝 / 现金 / 银行卡）；
- 客户端 Picker 改为读下发列表；
- 老数据保留原值，分析时走"归一化映射"，识别不了归「其他」。

### 4.4 索引（不做这个，数据一多就慢）

- `CREATE INDEX idx_records_spent_at ON records(spent_at)`
- `CREATE INDEX idx_records_cat_spent ON records(category_id, spent_at)`

### 4.5 现有实现要修的地方

- `GetExpenseTrend` 里 `_store.All()` 全表进内存 + LINQ → 改下推到 SQL `GROUP BY`。
- `ByDay(DateTime.Now)` 依赖机器时区 → 统一到 UTC+8 工具方法。

## 5. 接口设计（proto 草案）

```proto
service AnalysisService {
  rpc GetSpendingStructure (StructureRequest) returns (StructureResponse);
}

message StructureRequest {
  optional string period = 1;   // today | week | month | year
}

message CategorySlice {
  optional int32  category_id = 1;
  optional string name        = 2;
  optional string icon        = 3;
  optional double amount      = 4;   // 元，2 位小数
  optional double ratio       = 5;   // 0~1
  optional int32  count       = 6;   // 笔数
  optional double prev_amount = 7;   // 上一周期同期
  optional double delta_ratio = 8;   // 变化率，如 0.23 = +23%
  optional bool   has_prev    = 9;   // false 时客户端显示 "—"
}

message PayMethodSlice {
  optional string name   = 1;
  optional double amount = 2;
  optional double ratio  = 3;
  optional int32  count  = 4;
}

message StructureResponse {
  optional string period      = 1;
  optional int64  range_start = 2;   // 实际统计区间，客户端用来显示"10-01 ~ 10-18"
  optional int64  range_end   = 3;
  optional double total       = 4;
  optional int32  count       = 5;
  optional double daily_avg   = 6;
  optional double prev_total  = 7;
  optional double delta_ratio = 8;
  optional bool   has_prev    = 9;
  repeated CategorySlice  categories  = 10;
  repeated PayMethodSlice pay_methods = 11;
  optional int64  generated_at = 12;  // 服务端生成时间，客户端显示"数据截至"
}
```

**取舍说明**：一次 RPC 返回整页所需全部数据。手机上打 3~4 个 RPC 会让页面出现"部分区域先出来、部分区域还在转圈"的割裂感，且弱网下失败率翻倍。

## 6. 服务端结构

```
Analysis/
  SpendingAnalyzer.cs     纯计算：输入区间内明细 + 上一周期明细 → 结构结果
  PeriodResolver.cs       档位 → [start,end) + 上一周期区间（口径唯一来源，可单测）
Data/
  CategoryStore.cs        categories 表读写
Services/
  AnalysisServiceImpl.cs  只做：解析 period → 取数 → 调用 Analyzer → 转 proto
```

为什么单独拆 Analyzer：口径能写单元测试（"跨年边界对不对""占比是否加到 100%"），将来电脑端要出报表直接复用，不用再写一遍 SQL。

## 7. 手机端页面

- **位置**：`AppShell` 新增「统计」Tab（第 3 个）
- **结构（从上到下）**：
  1. 四段切换：今日 / 本周 / 本月 / 本年
  2. 大数字：总支出 + 一行小字"比上月同期 ↑12.3%"
  3. 统计范围："10-01 ~ 10-18 · 共 42 笔 · 日均 ¥86.5"
  4. 分类榜：横向占比条 + 名称 + 金额 + 占比 + 环比箭头
  5. 支付方式：横向占比条（可折叠，默认展开）
- **图表**：v1 用原生 `ProgressBar` 画占比条，**不引图表库**。你现在的包 18.6 MB，图表库少说加 1~3 MB，而结构分析根本不需要折线/饼图。
- **刷新**：进页面自动拉；下拉刷新；切档位立即重拉（带 300ms 防抖，防止连点）。
- **缓存**：只缓存**分析结果**（按 period 存一份 JSON），不缓存明细——与"手机不存完整历史"的原则一致。
- **降级**：请求失败 → 显示缓存 + "离线 · 数据截至 10-17 22:10"；无缓存 → 空态 + 重试按钮。
- **空态**：区间内无记录 → "这段时间还没有支出，去记一笔"+ 跳转按钮。

## 8. 验收标准（可测，不是"看起来对"）

1. 同分类记 3 笔（1.1 + 2.2 + 3.3）→ 分类金额 6.6，占比 = 6.6 / 总额，误差 < 0.01。
2. 各分类占比之和 = 100%（允许 ±0.1% 的展示误差）。
3. 23:59:59 记的账计入当天；00:00:00 计入次日。
4. 周一 00:00 记的账，"本周"包含它；周日 23:59 的账，上周不包含它。
5. 上月同期无数据 → 界面显示"—"，不显示"↑100%"。
6. 分类被停用/删除后，历史账单仍计入总额（归「未分类」），总额不变。
7. 断网打开统计页 → 3 秒内显示缓存 + 离线标识，不白屏、不转圈卡死。
8. 1 万条历史数据下，本机该接口响应 < 200ms。
9. 手机端把 Picker 的分类改成服务端下发后，7 个分类的 id 与历史数据完全一致（不出现"餐饮变交通"）。
