## 1. 数据模型

### 1.1 为什么仍然要手写迁移

`sqlite-net-pcl` 的 `CreateTable<T>()` **确实会给老表补列**，但补出来的是「可空、无默认值」——老数据那一批行会是 `NULL`。而 `WHERE direction = 0` 匹配不到 `NULL`，结果是**统计静默漏掉全部历史账单**（不报错，数字就是偏小）。

所以迁移仍然手写，但形态是"两条都做"：

```csharp
// 列不存在 → 显式 ALTER，带 DEFAULT 0（老行直接就是 0）
// 列已存在 → 兜底 UPDATE 把残留的 NULL 回填（覆盖 CreateTable 自动补列的情况）
if (!cols.Contains(column)) Exec($"ALTER TABLE {table} ADD COLUMN {column} {ddl}");
else                        Exec($"UPDATE {table} SET {column} = {fill} WHERE {column} IS NULL");
```

`ALTER TABLE ... ADD COLUMN` 在 SQLite 里**不能加 NOT NULL 而不给默认值**，`DEFAULT 0` 是硬性要求。

```csharp
// Data/Db.cs —— 迁移骨架（服务端）
private void Migrate()
{
    EnsureColumn("records", "direction",  "INTEGER NOT NULL DEFAULT 0", "0");
    EnsureColumn("records", "updated_at", "INTEGER NOT NULL DEFAULT 0", "created_at");
    EnsureColumn("records", "deleted",    "INTEGER NOT NULL DEFAULT 0", "0");
    EnsureColumn("things",  "updated_at", "INTEGER NOT NULL DEFAULT 0", "created_at");
    EnsureColumn("things",  "deleted",    "INTEGER NOT NULL DEFAULT 0", "0");

    // 老数据 updated_at 用 created_at 兜底，否则首次版本比较会把老记录全判成"过期"
    _db.Execute("UPDATE records SET updated_at = created_at WHERE updated_at = 0");

    _db.Execute("CREATE INDEX IF NOT EXISTS ix_records_spent     ON records(spent_at)");
    _db.Execute("CREATE INDEX IF NOT EXISTS ix_records_dir_spent ON records(direction, spent_at)");
    _db.Execute("CREATE INDEX IF NOT EXISTS ix_records_cat_spent ON records(category_id, spent_at)");
    _db.Execute("CREATE INDEX IF NOT EXISTS ix_things_occurred   ON things(occurred_at)");

    SeedCategories();   // INSERT OR IGNORE，可重复跑
}
```

**为什么 `direction` 要存在分类上而不是只存在记录上**：录入页要按方向分成两组 chips；服务端要能校验"支出记录不能引用 101 号分类"。只靠 id 分段能"算出来"，但算出来的是约定，查出来的才是约束。

### 1.3 金额精度：不改字段，改聚合方式

**结论：不把 `amount` 改成整数分，只在聚合时转成分。**

- 好处：零迁移、零 proto 破坏、老数据不动；`SUM(CAST(ROUND(amount*100) AS INTEGER))` 得到的是精确整数分，不会出现"各分类加起来 99.98%"。
- 风险边界：单笔 `double` 存储仍是近似值，但 `ROUND(x*100)` 在金额 < 9×10¹³ 时能精确还原分，个人账本永远碰不到上限。
- 配套约束：**录入时限制两位小数**，否则 `12.345` 会被静默按 12.35 记账（第三位消失得毫无提示）。

```sql
-- 今日支出（分）
SELECT COALESCE(SUM(CAST(ROUND(amount*100) AS INTEGER)),0)
FROM records
WHERE direction = 0 AND deleted = 0
  AND spent_at >= @from AND spent_at < @to;
```

所有新增接口一律返回 `*_cents`（int64）；老接口（`GetExpenseTrend` 的 `double amount`）保持不动，避免破坏现有调用。这个"新旧并存"要写进注释，否则半年后有人以为这是两套口径。

## 2. proto 定稿

### 2.1 字段变更（4 处）

```proto
message Record {
    optional string id = 1;
    optional double amount = 2;
    optional int32  category_id = 3;
    optional string note = 4;
    optional int64  spent_at = 5;
    optional string pay_method = 6;
    optional int64  created_at = 7;

    optional int32 direction = 8  [default = 0];      // 0 支出 / 1 收入
    optional int64 updated_at = 9;                     // 最后修改时间（毫秒）
    optional bool  deleted = 10   [default = false];   // 上传时置 true = 软删
}

message Category {
    // 1~5 不变
    optional int32 direction = 6 [default = 0];        // 0 支出 / 1 收入
}
```

兼容性：proto2 的 `optional` + `default`，老客户端不传这三个字段 → 服务端读到 `Direction=0 / UpdatedAt=0 / Deleted=false`，行为等于"支出、无版本、未删"，正是老数据想要的。**不需要数据迁移。**

`UpdatedAt = 0` 的服务端处理：视为"未知版本，直接接受"（老客户端不会传），避免老包被版本校验全部拒绝。

### 2.2 新增 RPC

金额一律走 `int64` 分，不用 `double`：`0.1+0.2` 那点误差会在"各分类占比加起来是 99.98%"上暴露出来，用户一眼就能看见。

**两个设计取舍**：

1. **手机端的编辑/删除不走 `SaveRecord`/`DeleteRecord`**，仍走 `UploadRecords`（把 `deleted=true`、新 `updated_at` 塞进批次）。原因：手机要能离线改，改了等下次上传即可；而单条 RPC 意味着离线时无路可走。
2. **管理端反之**，走单条 RPC。它在线上、要立刻生效、要拿到明确的校验错误文案（"分类已停用"这种话必须显式回给表单，不能靠 `failed_ids` 猜）。

两个入口，一套 `RecordStore.Save()`，不能各写一份校验。

### 3.1 `Period`：口径只有一处

```csharp
public static class Period
{
    public static readonly TimeSpan Cst = TimeSpan.FromHours(8);

    /// 东八区的"今天 00:00"，与机器时区无关
    public static DateTimeOffset StartOfDay(DateTimeOffset instant)
    {
        var local = instant.ToOffset(Cst);
        return new DateTimeOffset(local.Year, local.Month, local.Day, 0, 0, 0, Cst);
    }

    public static (long from, long to) Today(DateTimeOffset now)
    {
        var d = StartOfDay(now);
        return (d.ToUnixTimeMilliseconds(), d.AddDays(1).ToUnixTimeMilliseconds());
    }

    /// 判断某时间戳是否属于"今天"（手机端可编辑窗口用它）
    public static bool IsToday(long unixMs, DateTimeOffset now) { ... }
}
```

**为什么不用 `DateTime.Now`**：现有的 `GetExpenseTrend` 用的是机器本地时间。你哪天把服务端挪到一台 UTC 的机器上（或云主机），"今天"就整体偏 8 小时，历史数据看起来像丢了一天。这个常量必须只有一处定义。

### 3.2 `SpendingAnalyzer`：纯函数

```csharp
public static class SpendingAnalyzer
{
    public static TodaySummary Summarize(IEnumerable<RecordRow> rows, (long from, long to) range, DateTimeOffset now)
    {
        long expense = 0, income = 0; int count = 0;
        foreach (var r in rows)
        {
            if (r.Deleted != 0) continue;
            if (r.SpentAt < range.from || r.SpentAt >= range.to) continue;
            var cents = Cents(r.Amount);
            if (r.Direction == 0) { expense += cents; count++; } else income += cents;
        }
        return new TodaySummary(range.from, range.to, expense, income, count, now.ToUnixTimeMilliseconds());
    }

    public static long Cents(double amount) => (long)Math.Round(amount * 100, MidpointRounding.AwayFromZero);
}
```

无 IO、无 `DateTime.Now`、无 SQL —— 因为这三样是统计口径出错的主要来源。

**单测清单（口径边界，各一条）**：
- `23:59:59.999` 属于今天；`次日 00:00:00.000` 不属于今天
- 金额 `0.1 + 0.2` 两笔求和 = `30` 分，不是 `30.000000000000004`
- 收入不计入 `expense_cents`，也不计入 `expense_count`
- `deleted=1` 的记录两边都不算
- 传入 UTC 时间 `2026-01-01T16:30:00Z` → 东八区属于 `2026-01-02`

## 4. 统一写入路径：`RecordStore.Save()`

管理端、手机端上传、补录，全部落到这一个方法。校验顺序固定（先便宜后贵）：

```csharp
public SaveResult Save(RecordRow incoming)
{
    var now = DateTimeOffset.UtcNow.ToUnixTimeMilliseconds();

    // 删除请求不校验业务字段 —— 分类可能已停用，但删必须删得掉
    if (incoming.Deleted != 0) return SoftDelete(incoming.Id, incoming.UpdatedAt);

    if (incoming.Amount <= 0)                       return Fail("金额必须大于 0");
    if (HasMoreThanTwoDecimals(incoming.Amount))    return Fail("金额最多两位小数");

    var cat = _categories.Get(incoming.CategoryId);
    if (cat is null || cat.Enabled == 0)            return Fail("分类不存在或已停用");
    if (cat.Direction != incoming.Direction)        return Fail("分类与收支方向不匹配");

    if (incoming.SpentAt > now + 5 * 60_000)        return Fail("消费时间不能晚于当前时间");
    if (incoming.SpentAt < 946684800000L)           return Fail("消费时间早于 2000 年，请检查");
    if ((incoming.Note?.Length ?? 0) > 200)         return Fail("备注不能超过 200 字");

    var old = Get(incoming.Id);
    if (old is not null && incoming.UpdatedAt != 0
        && old.UpdatedAt != 0 && incoming.UpdatedAt < old.UpdatedAt)
        return Conflict(old);   // 服务端更新 → 拒绝，让客户端去拉最新

    if (incoming.UpdatedAt == 0) incoming.UpdatedAt = Math.Max(now, old?.UpdatedAt ?? 0);
    if (incoming.CreatedAt == 0) incoming.CreatedAt = old?.CreatedAt ?? now;

    Upsert(incoming);
    return Ok();
}
```

三条容易被省略但必须有的：

1. **删除先于校验**。否则"某分类停用后，该分类下的记录删不掉"，会出现删不掉的数据。
2. **未来时间容差 5 分钟**。手机时钟可能快几十秒，卡死 0 容差会让人莫名其妙记不上账。
3. **`UpdatedAt = 0` 视为未知版本直接接受**。老客户端不传该字段，如果严格比较会把老包全部拒绝。

## 5. 手机端

### 5.1 本地表迁移（同样是手写 ALTER）

`records` 加 `Direction INTEGER NOT NULL DEFAULT 0`、`UpdatedAt INTEGER NOT NULL DEFAULT 0`、`Deleted INTEGER NOT NULL DEFAULT 0`；`ThingsRecords` 加后两个。

本地不需要"删除待同步"这种额外字段 —— `Deleted` + `Synced` 两个布尔就能表达全部状态：

| Deleted | Synced | 含义 | 清理 |
|---|---|---|---|
| 0 | 0 | 新记的，待上传 | 永不清理 |
| 0 | 1 | 已同步 | 超过 30 天清理 |
| 1 | 0 | 已删，待上传删除 | 永不清理 |
| 1 | 1 | 服务端已删（墓碑） | 超过 30 天清理 |

所有列表查询默认加 `WHERE Deleted = 0`。

### 5.2 今日总额：先本地，再校正

```csharp
private async Task RefreshTodayAsync()
{
    // 1) 即时值：同步 SQL，0ms
    var (from, to) = Period.Today(DateTimeOffset.UtcNow);
    var local = _store.SumExpenseCents(from, to);      // 含未同步
    var pending = _store.CountPendingToday(from, to);
    RenderToday(local, pending);

    // 2) 校正值：静默请求，回来直接覆盖
    if (!_conn.IsOnline) return;
    try
    {
        var r = await _analysis.GetTodaySummaryAsync(new Empty());
        RenderToday(r.ExpenseCents, pending);          // 不比对、不弹窗
    }
    catch { /* 保持即时值，不显示错误提示 */ }
}
```

- 保存成功后**立即**跑一次第 1 步（不等网络），并排一次第 2 步。
- 显示：`今天 ¥86.50` + 小字 `4 笔 · 2 笔待同步`。
- 两者不一致时不解释、不弹窗。差异只会来自电脑端补录/修改，那是你自己刚做过的事。

### 5.3 可编辑窗口

```csharp
public static bool CanEditToday(long spentAt, DateTimeOffset now)
    => Period.StartOfDay(now).ToUnixTimeMilliseconds()
       == Period.StartOfDay(DateTimeOffset.FromUnixTimeMilliseconds(spentAt)).ToUnixTimeMilliseconds();
```

用固定 UTC+8，不用设备时区。设备在别的时区时，"手机上的今天"和"服务端的今天"必须是同一天，否则会出现"手机能改、服务端拒收"。

编辑后：`Synced = 0`、`UpdatedAt = now`；删除已同步记录：`Deleted = 1`、`Synced = 0`、`UpdatedAt = now`。

### 5.4 30 天镜像 + 清理

```csharp
public async Task Mirror30DaysAsync()
{
    var today = Period.StartOfDay(DateTimeOffset.UtcNow);
    var from  = today.AddDays(-29).ToUnixTimeMilliseconds();   // 含今天共 30 天
    var to    = today.AddDays(1).ToUnixTimeMilliseconds();     // 不含明天（左闭右开）

    var resp  = await _record.ListRecordsAsync(new ListRecordsRequest {
        From = from, To = to, IncludeDeleted = true, Direction = -1
    });
    var remoteIds = resp.Records.Select(x => x.Id).ToHashSet(StringComparer.Ordinal);

    await _db.RunInTransactionAsync(t =>
    {
        foreach (var p in resp.Records)
        {
            var local = t.Find<LocalRecord>(p.Id);

            // ★ 唯一会丢数据的地方：本地待同步的行永远不做覆盖
            if (local is not null && !local.Synced) continue;

            if (p.Deleted) { if (local is not null) t.Delete<LocalRecord>(p.Id); continue; }

            var row = ToLocal(p);
            row.Synced = true;
            row.SyncedAt = DateTimeOffset.UtcNow.ToUnixTimeMilliseconds();
            t.InsertOrReplace(row);
        }

        // 服务端已经不存在、但本地还留着的已同步行 → 删掉
        var stale = t.Table<LocalRecord>()
                     .Where(x => x.Synced && x.SpentAt >= from && x.SpentAt < to)
                     .ToList()
                     .Where(x => !remoteIds.Contains(x.Id));
        foreach (var s in stale) t.Delete<LocalRecord>(s.Id);
    });

    PruneLocalCache();
}

/// 只删本地副本，绝不调服务端删除接口
public int PruneLocalCache()
{
    var cutoff = Period.StartOfDay(DateTimeOffset.UtcNow).AddDays(-30).ToUnixTimeMilliseconds();
    return _db.Execute("DELETE FROM records WHERE Synced = 1 AND SpentAt < ?", cutoff);
}
```

三个必须遵守的细节：

1. **方法名必须是 `PruneLocalCache`**。叫 `DeleteRecords` 的那天，就会有人把它接到服务端删除接口上 —— 那是真删，删的是唯一的账本。
2. **清理条件必须带 `Synced = 1`**。先删老数据再判断同步状态，会把"出差两周没连上服务端"的未同步记录删干净，那是真正无法恢复的丢数据。
3. **先镜像后清理**。反过来会先删掉刚被服务端更新过的行，多一次多余往返。

调用时机：App 启动后（后台线程）、同步成功后、从"记录页"返回"概览页"时（防抖 30 秒）。

### 5.5 上传与冲突处理

`UploadRecords` 现在要带 `Deleted` / `Direction` / `UpdatedAt`。响应处理比现在多一条：

```
failed_ids 为空            → 全部标记 Synced=1, SyncedAt=now
failed_ids 含某 id         → 保留 Synced=0，下次重试（现有逻辑不变）
error_msg 含 "conflict"    → 不要重试！标记 Synced=1，然后单条拉取覆盖本地
```

最后一条很关键：版本冲突如果重试，会变成死循环（本地永远是旧版本，永远被拒）。正确做法是"承认自己过期"，拉服务端的版本覆盖。

## 6. 管理端（Razor Pages）

### 6.1 工程改动（唯一一处结构变更）

`PersonalHub.Server.csproj`：`Sdk="Microsoft.NET.Sdk"` → `Sdk="Microsoft.NET.Sdk.Web"`。

原因：`.cshtml` 需要 Razor 编译，`Microsoft.NET.Sdk` 不带 Razor 任务。`Microsoft.NET.Sdk.Web` 是官方做法，`Grpc.AspNetCore` 与 gRPC 端点在同一宿主里继续工作，不需要拆项目。

风险提示：
- 首次切换后要确认 `WebApplication.CreateBuilder` 的 content root 仍指向项目目录（Web SDK 会改这个默认值），否则 `Pages/` 找不到。
- Web SDK 会引入 `wwwroot` / `appsettings.json` 约定。当前项目没有这两样，不冲突，但**不要**顺手加 `app.UseStaticFiles()` 之外的东西。

### 6.2 路由与职责

| 路由 | 方法 | 职责 | 依赖 |
|---|---|---|---|
| `/` | GET | 概览：今日（复用 `GetTodaySummary`）、本月支出/收入/结余、最近 5 条 | Analyzer + Store |
| `/records` | GET | 列表：`from`/`to`/`direction`/`categoryId`/`payMethod`/`q`/`page`，每页 50 | `ListRecords` 语义 |
| `/records/edit?id=` | GET/POST | 有 `id` 编辑，无 `id` 补录 | `RecordStore.Save()` |
| `/records/delete` | POST | 软删，回列表 | `RecordStore.SoftDelete()` |
| `/categories` | GET | 只读展示（维护留 P1） | `CategoryStore` |
| `/records/trash` | — | P2，先不做 UI，`deleted=1` 已在库里 | — |

### 6.3 三条硬约束

1. **不写裸 SQL**。页面只调 `RecordStore`，校验与手机端完全同一份。否则会出现"手机不让存 0 元，网页能存进去"，统计当场错。
2. **校验错误要回显在表单上**，不能 `catch` 后统一显示"保存失败"。`SaveResult.Error` 已经是人话（"分类已停用"），直接 `ModelState.AddModelError`。
3. **CSRF 与绑定范围**。Razor Pages 默认开防伪令牌；Kestrel 已监听局域网地址（`PrintBanner` 打印内网 IP），所以手机同 Wi-Fi 能打开 —— 也意味着**同一 Wi-Fi 下任何设备都能改你的账**。R1 接受这个风险（仅家庭网络），但要在页面顶部常驻一行提示，别让自己以后忘了。

### 6.4 实际实现（落地后补充的三条，都是踩过才知道的）

**① 必须开两个端口，不能一个端口兼顾。**

gRPC 强制 HTTP/2，浏览器只讲 HTTP/1.1。不开 TLS 就没有 ALPN，同一个端口没法同时服务两者；而 `HttpProtocols.Http1AndHttp2` 在无 TLS 时 Kestrel 会**退化到 HTTP/1.1**，手机端会直接报 "HTTP/2 is not supported"（这个错看起来像客户端问题，实际是服务端协议配置）。

所以：

| 端口 | 协议 | 谁用 |
|---|---|---|
| `port`（默认 5000） | HTTP/2 | 手机 gRPC |
| `port + 1`（默认 5001） | HTTP/1.1 | 浏览器管理端 |

可用 `PERSONALHUB_WEB_PORT` / `--web-port` 覆盖。启动横幅会同时打印两组地址。

**② content root 要钉死在程序目录，否则样式会静默失效。**

`WebApplication.CreateBuilder(args)` 的默认 content root 是 `Directory.GetCurrentDirectory()`。从仓库根目录启动时，`wwwroot` 会被解析到仓库根而不是 `bin`，结果是**页面 200、CSS 404，而且不报任何错**。现在显式写成：

```csharp
WebApplication.CreateBuilder(new WebApplicationOptions
{
    Args = args,
    ContentRootPath = AppContext.BaseDirectory,
});
```

同时 csproj 要让 `wwwroot` 跟着 exe 走（Web SDK 默认只复制到 publish 目录），并显式 `app.UseStaticFiles()`。

**③ 列表的筛选在页面层拼，SQL 在 `RecordStore.Search()` 里。**

页面只负责把 query string 变成参数，不拼 SQL；`Search()` 返回 `(Items, Total)`，因为页面要显示"共 N 条 / 3 页"，而 `ListRows` 是给镜像同步用的、不能有分页语义。两者混用会得到一个"镜像只拉 50 条"的隐蔽 bug。

### 6.5 现在的路由

| 路由 | 说明 |
|---|---|
| `/` | 今日三数 + 本月三数（含环比/日均）+ 本月分类/支付方式占比 + 最近 5 条 |
| `/records` | 区间/方向/分类/关键字筛选，每页 50，勾选「显示已删除」可看墓碑 |
| `/records/edit?id=` | 有 id 编辑，无 id 补录；错误直接回显在表单上 |
| `POST /records?handler=Delete` | 软删，带 `returnUrl` 回到原筛选条件 |
| `/categories` | 分类只读（id/方向/状态/排序/记录数） |

## 7. 手机端页面树

```
AppShell（底部两项，按「读 / 写」分工，不按记录类型分）
├─ Tab 概览 (MainPage)              读：今日 / 本月三数 / 分类占比 / 最近 5 条 / 同步状态
└─ Tab 记录 (RecordHubPage)         写：记录类型目录
   ├─ entry/expense → RecordEntryPage     顶部 支出|收入 切换，分类 chips
   └─ entry/thing   → RecordDothingPage   事件反思
```

**Tab 为什么只有两项、录入页为什么不在 TabBar 里**：
类型会一直加（习惯 / 体重 / 阅读 / 复盘…），按类型分 Tab 迟早放不下，而且每加一种都要改导航、重新发版。
所以 TabBar 只按「读 / 写」分工，类型全部挂到 `Services/RecordCatalog.cs` 这张表里。

**新增一种记录类型 = 三处、都不是导航**：
1. `RecordCatalog.Build()` 加一条（标题 / 副标题 / 图标 / 路由 / 小字 / 待同步计数）；
2. `AppShell.RegisterRoutes()` 加一行 `Routing.RegisterRoute(route, new ServiceRouteFactory(typeof(XxxPage)))`；
3. `MauiProgram` 加一行 `AddTransient`，页面本身实现录入。

**目录项自带的两条信息**（这是它不只是"菜单"的原因）：
- 小字：`今日支出 ¥12.30 · 收入 ¥100.00` / `今日已记 2 条` —— 回到目录就知道有没有漏记；
- 徽标：`N 条待同步` —— 进页面时顺手静默同步一次，传完立即刷新。

**路由页必须走 DI 创建**：`Routing.RegisterRoute(route, typeof(Page))` 的默认实现可能去找无参构造，
而录入页都要注入 Store / 同步器 → 运行期 `MissingMethodException`。
这里显式用 `ServiceRouteFactory`（读 `IServiceProvider`）创建，不依赖 MAUI 版本行为。

`RecordEntryPage` 本轮改动：
1. 顶部 `支出 | 收入` 分段控件；切换时重建 chips（数据来自 `GetCategories`，不再硬编码）
2. 金额输入框置顶，`Keyboard=Numeric`，最多两位小数
3. 分类 chips（固定顺序 = 位置记忆稳定，不按频次重排）
4. 时间折叠成一行，默认"现在"
5. 顶部常驻今日总额 + 待同步笔数
6. 保存后留在页面、清空金额与备注
7. 今日列表每行：`[编辑] [删除]`，仅今日可用（其余行按钮置灰并显示"去电脑改"）

## 10. 已知的坑（按会咬人的概率排序）

1. **`CreateTable` 不补列** → 旧库直接 `no such column`。迁移必须在第 1 步做完再动别的。
2. **镜像时覆盖了 `Synced=0` 的行** → 用户刚记的账被服务端的旧版本覆盖，且不会有任何报错。这是唯一会造成"数据消失"的 bug。
3. **清理条件漏了 `Synced=1`** → 删掉唯一副本。
4. **版本冲突重试成死循环** → 见 5.5，冲突不是重试能解决的。
5. **切换 Web SDK 后 content root 变化** → 页面 404，但服务端启动正常，容易看半天。
6. **毫秒/秒混用**（`ThingRecord.CreatedTimestamp` 曾经就是秒）→ 排序和按天分组集体错位，且症状分散、极难定位。
7. **`ROUND` 之前就 `CAST`** → SQLite 里 `CAST(amount*100 AS INTEGER)` 是截断，`0.29` 会变 28 分。必须先 `ROUND` 再 `CAST`。
8. **默认值写成了"方便值"而不是"安全值"** → `include_deleted` 一度默认 `true`，结果"忘记传参"的调用方会拿到全部墓碑记录。默认值应该让"忘了传参"退化到最安全的行为（少拿墓碑），需要墓碑的一方显式开启。这条是第一轮端到端测试实测发现的。
9. **gRPC 和网页挤同一个端口** → 无 TLS 时 `Http1AndHttp2` 会退化到 HTTP/1.1，手机端报 "HTTP/2 is not supported"。必须分两个端口。
10. **content root 跟着当前工作目录跑** → 从仓库根启动时 `wwwroot` 找不到，页面 200 但 CSS 404，且不报错。钉死 `AppContext.BaseDirectory` + csproj 复制 `wwwroot` + 显式 `UseStaticFiles()`。
11. **在管理端直接改"已删除"的记录** → 等于用编辑悄悄复活一条记录，而手机镜像认为 `deleted=1` 就该消失，两边会反复打架。现在编辑页遇到 `deleted=1` 直接拒绝并提示。
