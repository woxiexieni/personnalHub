> 
> 两个独立通道：
> 通道 A：**HTTP 通道（仅本机，业务程序 → 监控服务，单向上报状态）**

### 通道 A：HTTP 上报接口（PC 服务端【接收】业务程序的数据）

> 
> 服务端监听：`http://127.0.0.1:5000/api/task/report`
> 方法：POST，Content-Type: `application/json`
> ✅ 这就是**PC 服务器接收业务程序的数据结构**

#### 请求 JSON（业务程序 POST 提交，服务端接收并解析）

```
{
  "task_state": 1,
  "progress_percent": 35.6,
  "processed_count": 356,
  "total_count": 1000,
  "cpu_usage": 42.3,
  "memory_usage_mb": 1240,
  "error_msg": ""
}
```

字段说明（服务端会校验字段类型，缺失字段使用默认值）

表格

| 字段 | 类型 | 说明 | 取值 | 是否必要 |
| --- | --- | --- | --- | --- |
| task_state | int | 任务状态 | 0 = 未启动，1 = 运行中，2 = 正常完成，3 = 异常崩溃，4 = 业务失联（业务程序**不要传 4，4 是监控服务自己判定生成**） | y |
| progress_percent | double | 进度百分比 | 0~100 | y |
| processed_count | long | 已处理样本数量 | >=0 |  |
| total_count | long | 总样本数量 | >=0 |  |
| cpu_usage | double | 本机 CPU 使用率 | 0~100 | y |
| memory_usage_mb | double | 内存占用，单位 MB | >=0 | y |
| error_msg | string | 错误信息 | 无错误填空字符串 | y,没有则为空 |
| timestamp | int64 | 时间戳 |  | y |

###### 控制指令包

| 字段      | 类型        | 说明     | 取值       | 是否必要 |
| --------- | ----------- | -------- | ---------- | -------- |
| cmd_type  | CommandType | 设备类型 | 默认为stop | y        |
| timestamp | int64       | 时间搓   |            | y        |
| token     | string      | 命令令牌 |            | y        |



##### HTTP 返回（服务端响应给业务程序）

- 成功：`200 OK`，返回 `{"code":0,"msg":"ok"}`
- 参数非法：`400 Bad Request`，返回 `{"code":-1,"msg":"invalid parameter"}`

> 
> 业务程序规则：周期性 POST 上报；**超过 60s 没有收到任何 HTTP 上报，监控服务自动将 task_state 置为 4（业务失联告警）**

### 通道 B：TCP 双向私有二进制协议（局域网，8888 端口）

帧统一格式（**双向共用同一个帧结构**）
`[4字节 大端长度头][2字节 CRC16-Modbus][Proto2消息体]`

1. 4 字节大端 uint32：后面【CRC (2 字节)+Proto 载荷】的总字节长度
2. 2 字节 CRC16-Modbus：**只对 Proto 二进制数据计算校验**
3. Proto2 二进制：二选一，两种消息类型

> 
> ⚠️ 关键问题：TCP 流收到二进制包之后，怎么区分是【服务下发的 TaskStatus】还是【客户端上传的 ClientCommand】？
> 之前漏掉这个！**必须增加消息类型标记，否则解析的时候分不清消息是哪一类**
> 两种方案，我们选一个：
> 方案 1：在 proto 外层帧增加 1 字节 MsgType（推荐，改动小）
> 新帧结构：`[4字节大端长度头][1字节 MsgType][2字节 CRC16-Modbus][Proto2消息体]`
> MsgType：
> 
> 
> - 0x01 → TaskStatus（服务端 → 安卓，状态包）
> - 0x02 → ClientCommand（安卓 → 服务端，指令包）
> 
> 
> 方案 2：在 proto 消息内部增加 type 字段。

> 
> 我建议方案 1，帧层面区分消息类型，解包第一时间就能知道消息种类，不用反序列化 proto 之后才判断，减少无效反序列化，适合工业通信。

#### Proto 定义（不变，保留两个独立消息）

```
syntax = "proto2";
package  motinor;

// 服务端 → 安卓客户端：任务状态包
message TaskStatus
{
    required int32 task_state = 1;
    required double progress_percent = 2;
    optional int64 processed_count = 3;
    optional int64 total_count = 4;
    required double cpu_usage = 5;
    required double memory_usage_mb = 6;
    required string error_msg = 7;
    required int64 timestamp = 8;
}

// 安卓客户端 → 服务端：控制指令包
message ClientCommand
{
    optional int32 cmd_type = 1; //1=停止任务，预留扩展
    optional int64 timestamp = 2;
    optional string token = 3; //鉴权token，用于指令校验
}
```

> 
> 新增：ClientCommand 增加 token 字段，安卓下发指令携带 token，服务端校验 token 是否匹配，不匹配直接丢弃指令。

#### TCP 两个方向的数据定义

1. **出站（PC 服务端 → 安卓客户端）**
封装内容：MsgType=0x01 + TaskStatus 序列化后的 proto 二进制，套入上面帧结构，推送给安卓。
2. **入站（安卓客户端 → PC 服务端，PC 服务端 TCP 接收的二进制包）**
PC 服务端 TCP 收到字节流，执行：
① 读取 4 字节大端长度头，得到后续包长度
② 读取 1 字节 MsgType
③ 读取 2 字节 CRC16
④ 读取 Proto 二进制载荷
⑤ 计算 Proto 载荷 CRC，和包内 CRC 对比；校验失败丢弃数据包，写日志
⑥ 根据 MsgType=0x02，将二进制反序列化为`ClientCommand`
⑦ 校验 token；token 合法，执行对应指令（停止任务）

> 
> 指令逻辑：收到停止指令后，监控服务**触发回调通知业务程序停止**。
> 👉 这里又一个关键点：监控服务收到安卓的停止指令，怎么通知业务程序停止任务？
> 候选方案：
> A：业务程序轮询监控服务 HTTP 接口，查询是否收到停止指令（简单，业务程序主动查询）
> B：监控服务反向 HTTP 推送给业务程序（业务程序需要开启 Http 监听，复杂度高）
> C：共享内存通信

你选择 A/B/C？

## 四、推送策略（不变）

1. 常态无状态变更：10s 推送 TaskStatus 包给所有在线客户端
2. 状态变更（任务完成、报错、失联）：**立即主动推送**
3. 新客户端 TCP 连接成功：服务端立刻下发当前最新 TaskStatus

## 五、参数配置（不变）

- TCP 端口：8888
- HTTP 上报端口：5000
- CRC：CRC16-Modbus

## 六、模块划分（不变）

1. HttpListener 模块：接收业务 POST 上报，更新内存任务状态
2. 任务状态管理模块：内存维护 TaskStatus，60s 超时检测判定失联
3. Hsl TCP 服务模块：TCP 会话管理，收发二进制帧
4. 协议编解码模块：帧打包 / 拆包，CRC 校验，Proto 序列化 / 反序列化
5. 指令处理模块：解析安卓 ClientCommand，Token 校验，下发停止信号给业务程序
6. 日志模块
